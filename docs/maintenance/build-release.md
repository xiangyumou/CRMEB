# CRMEB build and release

Use Node 20.19.0 and npm 10.8.2. From the repository root, run `bash scripts/build-release.sh`. This installs dependencies from lockfiles and builds the admin, H5 and MP-WEIXIN targets from source. It replaces `.build/release/` with `admin/`, `h5/`, `mpWeixin/`, the assembled `public/`, and `build.json`. No checked-in compiled frontend is used as a fallback.

The UniApp Vue 2 CLI version is pinned in `template/uni-app/package-lock.json`. Its H5 tree-shaking is disabled only in the temporary build input because its API scanner misses runtime APIs used by this project. `CRMEB_API_ORIGIN` defaults to `https://x-zoo.vip` and must be an HTTPS origin. `CRMEB_MP_APPID` is optional; without a real value the mini-program uses a test placeholder and `build.json` records `publishable:false`. This test package is not eligible for WeChat submission.

Build the application image from these inputs with `docker build --build-arg VCS_REF="$(git rev-parse HEAD)" -t crmeb-test .`. Run `sh docker/verify-image.sh crmeb-test`, `sh docker/run-regression.sh crmeb-test`, and `sh docker/verify-http-stack.sh crmeb-test`. To exercise image replacement against disposable persistent data, supply two different local images to `bash docker/upgrade-drill.sh IMAGE_A IMAGE_B`. Browser-check `/admin/`, `/pages/index/index`, a product page and a deep link at desktop and mobile widths before promoting a release.

CI builds both architectures after the frontend build, runs the regression suite and HTTP checks against the staged images, then pushes immutable `sha-<full commit>` tags. It creates `release.json` after obtaining the multi-architecture digest; `node scripts/verify-release.cjs .build/release/release.json` verifies the three frontend checksums. Publishing and promotion are separate: the automated workflow publishes the immutable `sha-<commit>` candidate and never moves the deployment tag. Promotion is a manual workflow (`.github/workflows/promote.yml`) that requires the candidate digest, the source commit and an acceptance id recorded in `docs/release-readiness.md`, verifies the digest is what that commit's tag resolves to, and moves the tag without rebuilding. The publish rules themselves live in `scripts/publish-release.sh` and are proven against a local registry by `tests/deployment/publish-release.sh`. The package `ghcr.io/xiangyumou/crmeb-release:sha-<full commit>` contains `/release/admin`, `/release/h5`, `/release/mpWeixin`, `/release/build.json`, `/release/release.json`, and `/release/deployment-config.tar.gz`. The matching GitHub Release exposes the manifest, deployment configuration, and three frontend archives to operators without GHCR package credentials. Keep these immutable packages and releases for at least 90 days; no automatic cleanup is configured. CI uses GHCR for transfer because GitHub Actions artifact storage is currently quota-blocked. Temporary `input-` and `ci-` tags are not production releases.

For the first production migration and subsequent `docker compose pull && docker compose up -d` updates, follow [the production runbook](../../deploy/production/README.md). A Compose image update does not perform database schema migrations or provide atomic zero-downtime deployment. Never use `docker compose down -v` in production.
