# CR-50-k2: the SMS resend guard is a check, then a separate write

**Stream:** K2 (hardening second pass) **Status:** RESOLVED 2026-09-23 by R1 — `claimResend` (`SET key token NX PX`) is the first thing `sendVerificationCode` does; a budget or provider refusal hands the window back with a token-checked `releaseResend`; `issueCode` no longer writes the resend key. The pin is flipped; its barrier now holds each caller's first touch of the key (`PTTL` or `SET`), since the fixed code no longer reads before it writes. Three tests added in the same file (budget refusal, provider refusal, release never deletes a later claim).
**Files:** `next/packages/core/src/sms/sms.service.ts` (`sendVerificationCode`), `next/packages/core/src/sms/verification-code.ts` (`resendWaitMs`, `issueCode`)
**Pinned by:** `next/packages/core/src/sms/sms.resend-race.int.test.ts`, `it.fails` "CR-50-k2 — the resend guard is a check, then a separate write > costs one SMS when six taps all read the resend key before any writes it"

## What

STAB-001 (ten consecutive shuffled rounds of the concurrency set) failed on
round 1:

```
FAIL |int| src/user/user.concurrency.int.test.ts > SMS codes > lets one of six sends through the resend guard
AssertionError: expected [ { expiresInSec: 300, …(1) }, …(4) ] to have a length of 1 but got 5
```

The test says "`SET NX` decides", but the code has no `SET NX`.
`sendVerificationCode` does this:

1. `resendWaitMs`: `PTTL sms:resend:<scene>:<phone>`, and refuse if it is positive;
2. check the three budget windows and read the `sms` config group;
3. `issueCode`: a `MULTI` that writes the code **and** `SET <resend key> 1 PX <resendMs>`,
   with no `NX`;
4. send.

Steps 1 and 3 are two separate round trips. Every caller that runs step 1
before the first caller reaches step 3 passes the guard. Each one mints a
code, overwrites the previous caller's code and sends an SMS. The per-phone
hourly budget (5) is the only thing that stops it. That budget check is a
`fixedWindow` counter, which is atomic, so it caps the burst at five.

The effect: a double-tap, or a script, costs up to five SMS instead of one.
Only the last code sent is valid, so the shopper who reads the first message
gets `验证码错误`.

## Reproduction

The pinned test wraps the harness's Redis so that each caller's `PTTL` on the
resend key waits until all six have read it. That is the interleaving a loaded
machine produces by chance, made deterministic. Result: `sms.sent` has 5
entries, expected 1. The control test in the same file (two sequential sends)
passes.

## Asked for

Make the guard the write:

```ts
// verification-code.ts
export async function claimResend(
  redis,
  scene,
  phone,
  resendMs,
): Promise<number /* wait ms, 0 = claimed */> {
  const ok = await redis.set(
    resendKey(scene, phone),
    "1",
    "PX",
    resendMs,
    "NX",
  );
  if (ok === "OK") return 0;
  const ttl = await redis.pttl(resendKey(scene, phone));
  return ttl > 0 ? ttl : 1;
}
```

`sendVerificationCode` calls it first. On any later refusal (a budget, or the
provider) it deletes the resend key again, which `discardCode` already does for
the provider path. `issueCode` then stops writing the resend key. Flip the
`it.fails` to `it`. The existing `user.concurrency` test then holds on every
schedule, not only on most of them.
