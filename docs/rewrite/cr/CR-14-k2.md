# CR-14-k2 — the client picks its own IP: the edge passes the client's `X-Forwarded-For` through and the app reads its first entry

**Stream:** K2 (hardening) **Status:** OPEN — for stream J (edge) and the orchestrator (`apps/web` request meta)
**Files:** `next/docker/edge/nginx.conf:77-78,93-94` (`X-Forwarded-For $proxy_add_x_forwarded_for`), `next/apps/web/app/api/v1/auth/_request.ts:17-22` (`clientIp`: first XFF entry), `next/apps/web/src/server/handle.ts:424` (audit `ip` = the raw XFF header)

## What

`$proxy_add_x_forwarded_for` **appends** to whatever `X-Forwarded-For` the
client sent. `clientIp()` takes the first entry — the one the client wrote. The
comment on `clientIp` says it "is trusted only because nothing but the reverse
proxy can reach the app", but the proxy forwards the client's value verbatim.

The attacker's request: `POST /api/v1/auth/sms-codes` with
`X-Forwarded-For: 198.51.100.<n>` and a different phone number each time. What
depends on that address:

- the per-IP daily SMS budget (`codePerIpPerDay`) — the only thing stopping one
  caller from sending codes to many different numbers (SMS cost, harassment).
  The per-phone budgets still hold;
- 访客数 on the dashboard (`user_visits.ip` for anonymous visitors);
- `users.last_login_ip` / `register_ip`, and `sms_logs.request_ip`;
- `audit_logs.ip`, which stores the **whole raw header**, so an admin can write
  any address into their own audit trail.

Whether production is exposed depends on the server's Traefik, which is not in
this repository: by default Traefik does not trust incoming `X-Forwarded-*` from
untrusted peers and rewrites the header, which would save it — but that is an
unversioned setting, and with `NEXT_EDGE_BIND` set to a public address (or any
other front) the edge is reached directly. The existing apps/web test
`user.int.test.ts::POST /api/v1/auth/sms-codes > counts the per-IP budget against the address the proxy forwarded`
asserts the first-entry rule, i.e. the current behaviour.

Route- and edge-level: outside K2 §1's test grant, no test committed.

## Asked for

Make the trust boundary explicit in versioned config:

- edge: `real_ip_header X-Forwarded-For; set_real_ip_from <Traefik's network>; real_ip_recursive on;`
  and send `X-Forwarded-For $remote_addr` (overwrite, not append) and
  `X-Real-IP $remote_addr` upstream;
- app: `clientIp()` reads `X-Real-IP` (set only by the edge), and `handle()`
  records that same value for the audit row rather than the raw header;
- update the apps/web test above to assert that a client-supplied XFF is
  ignored.

## Until then

Confirm on the server that Traefik's entrypoints do not set
`forwardedHeaders.insecure` or trust `0.0.0.0/0`, and keep `NEXT_EDGE_BIND` on
loopback.
