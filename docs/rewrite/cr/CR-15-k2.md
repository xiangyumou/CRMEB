# CR-15-k2 — the admin SSE stream outlives the session that opened it, one Redis connection per tab

**Stream:** K2 (hardening) **Status:** OPEN — for the orchestrator / N1 (notifications)
**Files:** `next/apps/web/app/admin-api/notifications/stream/route.ts:36-40` (session resolved once), `next/packages/core/src/notification/notification.stream.ts:82-102` (`redis.duplicate()` per subscriber)

## What

The bare SSE handler resolves the admin cookie **once**, at connect, and then
forwards that admin's channel until the client disconnects. Two consequences:

1. **Revocation does not reach it.** A stolen cookie whose owner then changes
   their password (every session revoked) keeps receiving the bell's payloads —
   titles and content of new orders, after-sales, low stock — for as long as the
   connection stays open. Disabling the account stops new fan-out to it
   (`notification.int.test.ts::admin fan-out and the SSE bell > leaves a disabled account out…`),
   a password change does not.
2. **No cap.** Each stream is its own `redis.duplicate()` connection. Any admin
   session can open streams in a loop until Redis `maxclients` or the web
   process's file descriptors run out, which takes sessions, rate limits and the
   queue down with it.

Route-level: outside K2 §1's test grant, no test committed. CR-32-k2 (a
different defect in the same route) is the e2e side's.

## Asked for

- Re-resolve the session on each keep-alive tick (every 25 s) and close the
  stream when it no longer resolves.
- One shared subscriber connection per process, fanning out in memory, instead
  of a connection per stream; or at minimum a per-admin cap (e.g. 5 open
  streams) enforced with a Redis counter.

## Until then

The admin UI opens one stream per tab; the exposure needs a valid admin cookie.
