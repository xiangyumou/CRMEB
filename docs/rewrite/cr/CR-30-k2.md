# CR-30-k2 — CR-5-k is still open: the scan-token mint names no audit target

**Stream:** K2 (hardening second pass) **Status:** RESOLVED — applied by the orchestrator at K2's merge (the route audits `scan-token:<8-char prefix>`; `AUDIT_EXEMPT` entry deleted)
**Supersedes:** CR-5-k (addressed to F1, which merged without answering it)
**Files:** `next/apps/web/app/admin-api/attachments/scan-tokens/route.ts`

## What

The K2 brief lists CR-5-k as closed. It is not. On `rewrite/integration` (and on
`rewrite/ws-k2-hardening` after W4T) the route is still:

```ts
export const POST = handle(storageScanTokenCreate, (ctx, { query }) =>
  storage.scanTokenCreate(ctx, query),
);
```

`handle()` writes the audit row, but without a target, so the minting of a
bearer credential (an unauthenticated phone uploads into the library as that
admin with it) cannot be joined to the upload it enables. CR-5-k has the full
argument.

## Why the orchestrator

F1 has merged, and K may not edit production code. CR-17-k (the other 21
exemptions) was closed by E4; this one fell between the two.

## The patch

```ts
export const POST = handle(storageScanTokenCreate, async (ctx, { query }) => {
  const minted = await storage.scanTokenCreate(ctx, query);
  // Not the token: an audit row is read by more people than hold the credential.
  ctx.audit(`scan-token:${minted.token.slice(0, 8)}`);
  return minted;
});
```

The prefix is enough to find the mint from an upload's token; the full token
must never be written to `audit_logs`.

## What the guard does meanwhile

`route-hygiene`'s `AUDIT_EXEMPT` carries the entry as `pending(K)` pointing at
this CR, so the K2 merge cannot reach the required 0-pending run without it.
When the route calls `ctx.audit(…)` the guard **fails** until the entry is
deleted (new in K2: an exempt route that starts naming a target is stale). So
at K2's merge: apply the patch, delete the `scan-tokens` entry from
`next/guards/src/checks/route-hygiene.ts`, rerun `pnpm guards`.
