# CR-22-k2: nothing held a payment against a cancel under the order lock

**Stream:** K2 (hardening second pass, MUT-001) **Status:** test added in K2, ledger update for the orchestrator
**Files:** `next/packages/core/src/payment/payment.repo.ts` (`lockOrderForPayment`, unchanged), `next/packages/core/src/payment/payment.cancel-lock.int.test.ts` (new), `docs/rewrite/invariants.md` (PAYC-001 row)
**Found by:** MUT-001 mutant `order-lock`, which survived the first run

## What

`cancelOrder` locks the order (`SELECT … FOR UPDATE`). Under that lock it asks
the payment domain whether an attempt is open. That re-check protects anything
only if `startPayment` takes **the same row lock** before it reads the order.
The lock is `lockOrderForPayment`'s `.for('update')`.

Removing that one line passed every payment, cancel and concurrency test:

- `PAYC-001 — a create in flight is never stepped over`;
- `QUEUE-003 — a callback racing an order cancel`;
- the rest of `payment.int` and `payment.concurrency.int`.

These tests all order the two sides in time: the create is held at the gateway
boundary, or the callback arrives after the cancel. None of them has a payment
**reading the order while the cancel is between its check and its commit**,
which is the window the lock exists to close.

## Missing assertion, now added

`next/packages/core/src/payment/payment.cancel-lock.int.test.ts` (int project).
Describe block:
`PAYC-001 — a payment started while a cancel holds the order lock`.

It is deterministic and uses no sleeps. An `onOrderCancelled` hook runs inside
the cancelling transaction, after the transition and before the commit. From
there it starts `startPayment` on a separate pooled connection. It then polls
`pg_stat_activity` until PostgreSQL reports a backend waiting on a lock, with a
10 s ceiling.

- **"waits for the cancel to commit, then refuses: no attempt, no gateway order"**
  - The payment was blocked while the cancel held the row.
  - After the commit it rejects with `PAYMENT_ORDER_NOT_PAYABLE`.
  - The order is `cancelled`, there are no `payment_attempts` rows, the fake
    gateway holds no transaction, and there was no `/v3/pay/transactions/jsapi`
    call.
- **"lets the payment through once the cancel has lost"**
  - The hook throws, so the cancel rolls back. The payment that queued behind
    it proceeds: `pending_payment`, one `submitted` attempt.
  - This shows the lock is a queue, not a refusal.

With the mutant applied, the first test fails: the payment never blocks, it
reads `pending_payment`, and it opens a gateway order on an order that is
cancelled a moment later. Both tests pass on HEAD. Three back-to-back runs of
the lock, coupon and card mutants killed all three every time.
