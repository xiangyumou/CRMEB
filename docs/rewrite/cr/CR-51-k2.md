# CR-51-k2: COUPON-008's "limit above one" test asserts a schedule, not the invariant

**Stream:** K2 (hardening second pass) **Status:** OPEN, for the orchestrator (D owns `coupon` and has merged). This is a test defect, not a product defect.
**Files:** `next/packages/core/src/coupon/coupon.concurrency.int.test.ts` (`COUPON-008 — one user tapping 领取 twice > never lets simultaneous taps exceed a limit above one`)

## What

STAB-001 failed on round 2 (shuffle seed 2):

```
FAIL |int| src/coupon/coupon.concurrency.int.test.ts > COUPON-008 — one user tapping 领取 twice > never lets simultaneous taps exceed a limit above one
AssertionError: expected [ { …(2) }, { …(2) } ] to have a length of 1 but got 2
```

The template has `perUserLimit: 3`. Ten simultaneous claims from one user are
expected to produce exactly **one** wallet row. The comment explains why:
"`claim_slot` is computed from what is committed, so N simultaneous taps all aim
at the same slot and exactly one of them lands."

That holds only if every racer reads the committed slots before the first
winner commits. `runConcurrently` releases them from one barrier, but on a
loaded machine one racer can reach its read after the first winner's commit.
It then aims at slot 2, and it lands, legitimately. The product did the right
thing: two coupons, slots 1 and 2, limit 3 respected, supply decremented
twice. The assertion encodes the scheduling assumption, not the invariant.

## Asked for

Assert the invariant instead of a schedule:

```ts
const slots = (await walletRows()).map((row) => row.claimSlot).sort();
expect(report.fulfilled.length).toBeGreaterThanOrEqual(1);
expect(report.fulfilled.length).toBeLessThanOrEqual(3);
expect(slots).toEqual([1, 2, 3].slice(0, report.fulfilled.length)); // distinct, dense, within the limit
expect((await templateRow(templateId)).remainingCount).toBe(100 - report.fulfilled.length);
```

Then continue the sequential half from however many landed: claim until
`COUPON_PER_USER_LIMIT_REACHED`, and expect `[1, 2, 3]` and `remainingCount` 97
at the end. The file-level comment's "exactly one" line should say "at least
one and never more than the limit". Refusing remains the likely direction; it
is not a guaranteed one.

STAB-001 cannot go to 10/10 with this assertion as it is.
