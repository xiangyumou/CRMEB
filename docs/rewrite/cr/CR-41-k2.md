# CR-41-k2 — every product view takes a row lock on `products` to bump a counter `product_events` already records

**Stream:** K2 (hardening second pass, §4 load smoke) **Status:** OPEN — for stream A (catalog)
**Files:** `next/packages/core/src/catalog/catalog.storefront.service.ts` (`productDetail`, ~l. 188: `recordProductView` + `bumpProductViews` in one transaction), `next/packages/core/src/catalog/catalog.repo.ts` (`bumpProductViews`, ~l. 652)
**Evidence:** `next/load/REPORT.md` (run A and run B)

## What

`GET /api/v1/catalog/products/:id` writes twice on every view, inside one
transaction:

```sql
insert into "product_events" ("id", "product_id", "sku_id", "user_id", "order_id", "kind", "quantity",
  "amount", "cost_amount", "platform", "created_at")
values (default, $1, default, $2, default, $3, $4, default, default, $5, default)

update "products" set "views" = "products"."views" + $2 where "products"."id" = $1
```

The insert is the one decision 4 (`docs/rewrite/status/a.md`) asks for: browse
history and the traffic report both read `product_events`. The `UPDATE` keeps
a second copy of the same count on the product row itself. Every concurrent
view of one product takes the same row lock, and holds it until the
surrounding transaction commits.

It was the **second most expensive statement in the whole run**, although it
is a one-row primary-key update:

| Run | calls (= detail requests) | total ms | mean ms | a comparable PK update: `update "user_sessions" set "last_seen_at" = $1 where "id" = $2` |
| --- | ------------------------: | -------: | ------: | ---------------------------------------------------------------------------------------- |
| A   |                      2817 |   1041.7 |   0.370 | 7898 calls, mean 0.032 ms                                                                |
| B   |                      1834 |    828.5 |   0.452 | —                                                                                        |

That is 11–14× the cost of an equivalent single-row update, and the extra is
lock waiting. The seed has only 20 products, and 16 shoppers viewed them at
≈47 views/s. A promotion pushes everyone onto _one_ product, and then every
detail request queues behind that product's row lock. The page most likely to
be hot is the one that slows down. Each bump also writes a new `products`
tuple, a wide row with `slider_images` and prices, so the table bloats in
proportion to traffic rather than to edits.

Secondary, from the same `pg_stat_statements` dump (run A), and less certain:

- A detail request runs about 20 statements, all fixed in count, so this is
  not an N+1. `findSellableProduct`, `labelsFor`, `listSpecs`,
  `listVisibleSkus`, `listParams`, `protectionsFor`, `linkedIds`,
  `findDescription`, `reviewCountsFor`, `isFavorited`, the category links
  (`… where "product_id" = $1`, 2816 calls) and the two writes.
- The product row and its category links look like they are also read a second
  time through the batch loader: `select … from "products" … in ($1)` and
  `select "product_id", "category_id" from "product_categories_map" where
"product_id" in ($1)`, each 3920 calls ≈ detail 2813 + checkout preview 1131.
  Worth a look while the file is open. It is cheap (≈0.03 ms each), so no fix
  is asked for.

## Asked for

1. Drop the synchronous `UPDATE products SET views = views + 1` from the
   request path. `products.views` can be derived when it is needed: the admin
   list and the storefront card can read a periodically refreshed count from
   `product_events`, or a worker job can fold `product_events` into
   `products.views` in batches (one `UPDATE … FROM (SELECT product_id,
count(*) …)` per minute).
2. If a live counter is really wanted, increment it in Redis (`INCR`), and have
   the worker flush it. The shopper-facing `views` value is already one visit
   stale by design ("`views` is read before the increment").
3. A concurrency test in the catalog suite: N parallel detail reads of one
   product, asserting they do not serialize on a row lock. For example, assert
   no `pg_locks` wait on `products`, or assert the view rows all land while a
   separate transaction holds `SELECT … FOR UPDATE` on that product.
