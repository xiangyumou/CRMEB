# CR-21-k2: nothing tested that the pay client verifies the gateway's certificate

**Stream:** K2 (hardening second pass, MUT-001) **Status:** test added in K2, ledger update for the orchestrator
**Files:** `next/packages/core/src/wechat/wechat.pay.ts` (unchanged), `next/packages/core/src/wechat/wechat.pay.tls.test.ts` (new), `docs/rewrite/invariants.md` (TLS-001 row)
**Found by:** MUT-001 mutant `tls-peer-verification`, which survived the first run

## What

TLS-001 says the pay transport keeps certificate-chain and hostname
verification on. Its ledger test, `payment.config.test.ts::TLS-001 — no TLS
toggle, in any group this stream owns`, shows only that no config group can grow
a "verify SSL" switch. It says nothing about whether the client actually
verifies.

The mutant writes `process.env.NODE_TLS_REJECT_UNAUTHORIZED = '0'` into
`wechat.pay.ts`, right before its `fetch`. That turns verification off for the
whole process, and it passed every payment, refund and wechat test in the tree.
The reason: `startFakeWechatGateway` speaks plain HTTP, so no test ever
completed a TLS handshake with the pay client.

## Missing assertion, now added

`next/packages/core/src/wechat/wechat.pay.tls.test.ts` (unit project, no
network beyond loopback). Describe block:
`TLS-001 — the pay client refuses a gateway it cannot authenticate`.

- **The server.** An HTTPS server on `127.0.0.1` with a self-signed certificate
  for `localhost` (SAN `DNS:localhost`, `IP:127.0.0.1`). The certificate is
  minted per run from a fresh RSA key by a small DER builder, so no key material
  is stored in the repository.
- **Control test.** An `https.request` that is told to trust exactly that
  certificate (`ca`) gets its 200. This shows the server is sound.
- **Refusal tests.**
  - `createWechatPayClient(...).queryTransaction` against
    `https://localhost:<port>` must reject with `DomainError`
    `PAYMENT_STATE_UNKNOWN`, `details.reason === 'transport'`.
  - The server must have received **no request**, so the handshake is where it
    stopped.
  - The same holds for `closeTransaction`. A 204 means "closed" only over a
    channel that was authenticated.

With the mutant applied, both refusal tests fail: the request goes through, and
the client reads a response it should never have seen. They pass on HEAD.

## For the orchestrator

- **Ledger, TLS-001.** Append these to the test column:
  - `packages/core/src/wechat/wechat.pay.tls.test.ts::TLS-001 — the pay client refuses a gateway it cannot authenticate > refuses the handshake, so the query never reaches the server`
  - `… > refuses the close the same way — a 204 is only trustworthy over an authenticated channel`

  The config test stays; it guards the other half (no toggle).

- **Neighbouring gap, not addressed here.** The refund client and the OA/mini
  clients use the same platform `fetch`, and none of them has a TLS test. The
  mutant targets the pay client because MUT-001 names the pay transport. If
  TLS-001 is read as covering every outbound WeChat call, the same untrusted
  server fixture can be pointed at those clients.

## Neighbouring gap (R3, `5f188198d`)

The OA and mini-program client (`wechat.client.ts`) had the same hole and
carries the AppSecret on the query string of `/cgi-bin/token`,
`/sns/oauth2/access_token` and `/sns/jscode2session`.
`wechat/wechat.client.tls.test.ts` points each of its seven calls (oa token,
mini token, `oaCodeExchange`, `miniCode2Session`, `call`, `callBytes`,
`upload`) at an HTTPS server with an untrusted self-signed certificate and
requires a certificate error with nothing received; all seven fail under
`NODE_TLS_REJECT_UNAUTHORIZED=0`. The fixture moved to
`wechat/__fixtures__/untrusted-https.ts` (`wechat.pay.tls.test.ts` uses it too;
R2's refund client can). Ledger text for TLS-001 is in `status/r3.md`.
