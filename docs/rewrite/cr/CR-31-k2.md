# CR-31-k2 — the official-account media upload still calls `fetch` outside C's client

**Stream:** K2 (hardening second pass) **Status:** OPEN — for the orchestrator (C's seam; E3 merged)
**Carries:** CR-4-e2, which is cited in the code but was never filed as a file
**Files:** `next/packages/core/src/wechat-oa/wechat-oa.client.ts` (`uploadMedium`),
`next/packages/core/src/wechat/wechat.client.ts` (`WechatCoreClient`)

## What

K1 left `FETCH_ALLOW`'s `wechat-oa/` entry for "until E3 puts the outbound call
behind the seam". E3 merged; the call is not behind it. `uploadMedium` builds
a multipart request itself and calls `fetch` with a token from
`client.accessToken('oa')`, because `WechatCoreClient.call` speaks JSON only.

## Why it matters (and why it is not SSRF)

The URL is `new URL(path, config.apiBaseUrl)` — configuration, not user input —
so the SSRF rule the guard exists for holds. What the call misses is the
client's transport rules: the `40001 → drop the cached token and retry once`
path, the cross-process single flight and the TLS defaults. A stale token here
surfaces as `WECHAT_OA_API_FAILED 40001` and the operator presses the button
again; every other WeChat call recovers by itself.

## Asked for

An `upload(app, { path, query, field, bytes, filename, contentType })` method on
`WechatCoreClient` that shares `call`'s token handling and retry, and
`uploadMedium` rewritten on top of it. Then delete the `wechat-oa.client.ts`
entry from `FETCH_ALLOW` in `next/guards/src/checks/banned.ts` (the list is
exactly compared: the entry fails once the file stops calling `fetch`).

## What the guard does meanwhile

K2 narrowed the entry from the whole `wechat-oa/` directory to this one file
and made `FETCH_ALLOW` exactly compared, so no other file in the domain can call
`fetch` under its cover. It is not a `pending` item: the SSRF property the check
asserts is true today, and the CR is about retry semantics.
