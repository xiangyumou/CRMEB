# CR-53-k2: a stock reservation takes a second pooled connection while it holds the SKU row lock, and can wedge the pool for good

**Stream:** K2 (hardening second pass) **Status:** RESOLVED 2026-09-23 by R1 — (1) `ctx.config.getIn(tx, group)` reads through the caller's transaction on a cache miss and `warnOnLowStock` uses it; the pin is flipped (`6785b3708`); (2) `pnpm guards tx-pool` flags `ctx.config.get(` / `ctx.db` / `ctx.withTx(` inside any function taking `tx`, `Tx` or `DbOrTx`, with exact-compared lists; it found three more instances outside R1's ownership, filed as CR-1-r1 and pending on R2 (`1e49089e2`); (3) every pool has a 5 s acquire timeout and a 30 s `idle_in_transaction_session_timeout` (env-overridable) and listens for connection errors, proven in `catalog.stock.pool.int.test.ts` (`8b3a68eee`). `notification.send.ts:111` is not an instance (it runs after commit, with no transaction open); see CR-1-r1. **Severity: high.** The whole web process stops serving, with no recovery.
**Files:** `next/packages/core/src/catalog/catalog.stock.ts` (`reserve` → `warnOnLowStock`, line ~86), `next/packages/core/src/kernel/config-registry.ts` (`readRaw` reads `db`, not the caller's `tx`), `next/packages/db/src/client.ts` (`pg.Pool` with no acquire timeout)
**Pinned by:** `next/packages/core/src/catalog/catalog.stock.pool.int.test.ts`, `it.fails` "CR-53-k2 — a stock reservation never needs a second pooled connection > lets pool-max reservers of one SKU all finish when the config cache is cold"

## What

STAB-001 round 3 (shuffle seed 3) did not fail. It **hung**, for 15 minutes,
until K2 killed it, in
`order.concurrency.int.test.ts > sells ten units to exactly ten of twelve buyers`.
`pg_stat_activity` in the test database at that moment:

```
pid 121  idle in transaction  Client/ClientRead  update "products" set "price" = coalesce((select min(s.price) …   ← holds the SKU row lock
pid 123  active  Lock/transactionid  update "product_skus" set "stock" = "product_skus"."stock" - $1 where …   ← ×11
```

That is twelve connections, the harness pool's `max`, and every one of them is
stuck.

The mechanism:

1. `catalogStockPort.reserve(tx, orderId, lines, ctx)` decrements the SKU
   (`FOR UPDATE`-equivalent row lock, held until commit), then runs `rollupFor`,
   then `warnOnLowStock(tx, ctx, …)`.
2. `warnOnLowStock` starts with `await ctx.config.get(catalogConfig)`. The config
   service reads Redis. On a miss it runs `loadGroup(db, …)` on the **pool**, not
   on `tx`. The cache TTL is 5 minutes (`DEFAULT_TTL_MS`), so a miss happens
   every five minutes and after every config save.
3. If `max` transactions are in flight on the same SKU, the other `max - 1` hold
   pool connections while they wait for the row lock. The lock holder asks the
   pool for one more connection. None will ever be free: they are released only
   when the holder commits.
4. `pg.Pool` is created without `connectionTimeoutMillis`, so the acquire waits
   forever. No `idle_in_transaction_session_timeout` or `statement_timeout` is
   set, so PostgreSQL waits forever too.

In production the web pool is `DB_POOL_MAX` = 10 (`deploy/next/compose.yml`).
Ten concurrent checkouts of one SKU arriving as the catalog config cache
expires wedge the web process's pool permanently. Every later request that
touches the database hangs, and `/api/v1/health` does not notice, because it
does not use the database. A flash sale on one product is exactly this load
shape. The same pattern (a pool read from inside a transaction) exists wherever
`ctx.config.get` or `ctx.db` is used while a `tx` is open.
`notification.send.ts:111` is another instance on the paid path.

## Reproduction

The pinned test uses a pool of 3 and three reservers on one SKU. It holds the
lock holder's config-cache read until the other two are blocked on the row
lock. The outcome is `wedged` after 16 s, deterministically. It frees the
sessions with `pg_terminate_backend` so the file can tear down.

## Asked for

1. **The fix:** `warnOnLowStock` must not take a second connection while the
   lock is held. Either read `catalogConfig` **before** the conditional update,
   or give the config service a `getIn(tx, group)` that reads through the
   caller's transaction on a cache miss, and use it here and in
   `notification.send.ts`. Flip the `it.fails`.
2. **The class:** a guard (K owns `next/guards`, so this can come back as a
   K-stream task) that flags `ctx.config.get(` / `ctx.db` inside a function
   that has a `tx: Tx` parameter, with an allow-list for reads that are proven
   to happen before any lock.
3. **Defence in depth** (`packages/db`, orchestrator):
   - `connectionTimeoutMillis` on the pool (a few seconds), so a starved acquire
     becomes an error and a rolled-back transaction instead of a permanent hang;
   - `idle_in_transaction_session_timeout` (for example 30 s) as a connection
     option.
