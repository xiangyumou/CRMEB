# CR-40-k2 — the effects dispatcher drains at most 50 rows per 5 s, and a paid order records 6

**Stream:** K2 (hardening second pass, §4 load smoke) **Status:** RESOLVED 2026-09-23 by R1 (items 1, 2, 4) — `dispatchDueEffects` (`core/effects`) claims again while a batch comes back full, inside a `budgetMs` on `ctx.clock` (worker: 4 s under the 5 s repeat; `maxPasses` 100 as a hard stop); the run report and the `effects dispatched` log line carry `oldestDueAgeMs`; `/api/v1/readyz` carries `backlog.effectsOldestDueSeconds`, a detail that never fails the probe (an additive optional field on the readiness contract). Tests: `effects.int.test.ts::a dispatcher run drains while there is work (CR-40-k2)` (4, fake clock) and `apps/web/src/server/health.int.test.ts::… reports the effects backlog as a detail, never as a failing check (CR-40-k2)`. **Item 3 not done:** running one batch's handlers concurrently would let two effects of the same order (`order.auto-deliver`, its `notification.send`) run out of their recorded order, which is not trivial to prove harmless; with item 1 the ceiling is the handlers' own speed, not the tick.
**Files:** `next/apps/worker/src/jobs/system.effects.ts` (`repeat: { every: 5_000 }`, `batchSize` default 50, `concurrency: 1`), `next/packages/core/src/effects/index.ts` (`dispatchEffectsOnce`: one claim, handlers run one after another)
**Evidence:** `next/load/REPORT.md` (run A and run B)

## What

Every post-commit side effect goes through the `effects` table. The worker
drains it with one repeatable job that runs every 5 s. Each pass claims **one**
batch of 50 rows and returns, even when the batch was full. So one worker
container delivers at most **10 effects per second**, however long the queue
is. Handlers inside a batch run one at a time, so a slow handler lowers that
ceiling further.

Under the load smoke, the storefront recorded effects about ten times faster
than that:

```sql
insert into "effects" ("id", "scope", "scope_id", "event_type", "payload", "status", "attempts",
  "next_run_at", "last_error", "dispatched_at", "created_at", "updated_at")
values (default, $1, $2, $3, $4, $5, $6, $7, default, default, $8, $9) on conflict ("scope", …
```

| Run | Order + pay flows in the 60 s window | `insert into effects` calls | per flow | dispatcher claims (`select … from effects where status = $1 and next_run_at <= $2 … limit 50`) |                   rows claimed |
| --- | -----------------------------------: | --------------------------: | -------: | ---------------------------------------------------------------------------------------------: | -----------------------------: |
| A   |                                 1162 |                        6994 |      6.0 |                                                                                             12 | 600 (50 × 12, every pass full) |

Five seconds after the window closed, `effects` held (run A) **7944 pending**
and 666 done. Run B, which also broke the backlog down by type (974 paid
orders over smoke, warm-up and window), shows where the six rows per paid order
come from:

| scope / event_type                   | pending | done | per paid order |
| ------------------------------------ | ------: | ---: | -------------: |
| `notification` / `notification.send` |    3365 |  531 |            4.0 |
| `order` / `order.paid`               |     974 |    0 |            1.0 |
| `order` / `order.auto-deliver`       |     842 |  132 |            1.0 |

So one worker keeps up with about **1.7 paid orders per second** (10 ÷ 6),
before retries count. `order.paid` has no handler (CR-2-k2), so each of those
rows is claimed, retried with backoff and claimed again, up to 8 times. That
uses up more of the same 10 per second, which puts the steady-state ceiling
nearer 0.8 paid orders per second until CR-2-k2 is fixed.

The load rate here (≈19 paid orders/s on a 32-core machine) is far above what
the production shop sees on an ordinary day. The failure mode matters anyway,
because it shows up at the worst moment: in a promotion burst, 1000 orders in
ten minutes queue about 6000 effects. That takes **ten more minutes** to drain,
so buyers' 支付成功 notifications and every other post-commit effect arrive
minutes late. Nothing reports it: `/api/v1/readyz` looks at the worker's
heartbeat, not at the age of the oldest due effect.

## Asked for

1. **Drain while there is work.** When a pass claims a full batch, claim again
   right away instead of waiting for the next 5 s tick. Keep a time budget
   (for example 4 s, below the repeat interval) so a pass still always returns
   and a redeploy never waits on an unbounded drain, which is what the job's
   comment promises.
2. **Measure it.** Report the age of the oldest due `pending` row, both in the
   `effects dispatched` log line and as a `readyz` detail (a detail, not a
   failing check). A growing backlog should be visible before a customer
   notices it.
3. Optionally, run the handlers of one batch with a small bounded concurrency
   (2–4). The claim already uses `FOR UPDATE SKIP LOCKED` with a lease, so rows
   cannot be handled twice.
4. A test that queues more than one batch of due effects and asserts one
   dispatcher run leaves none due. It should use a fake clock, not wall time.

Fix CR-2-k2 (no handler for `order.paid` / `order.refunded`) either way. Until
then, every paid order also costs 8 dispatcher slots, spread over half an hour.
