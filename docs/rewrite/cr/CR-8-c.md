# CR-8-c — nothing calls `register<Domain>Domain()`, so no port and no effect handler exists in production

**Stream** C · **Target** `next/apps/worker/src/` and `next/apps/web/src/server/` bootstraps, plus a `pnpm gen` bucket (platform-owned) · **Severity** high, affects every stream

**Status:** applied — `pnpm gen` writes `packages/core/src/domains.gen.ts`, which imports every `src/<domain>/index.ts` and calls every `register<Name>Domain()` found by scanning the index source; `apps/web/src/server/handle.ts` and the worker container each `import '@shop/core/domains'` once at bootstrap, and this stream's module-scope stop-gap in the four payment/refund job files is removed.

## What

Every domain in the rewrite publishes a registration function — this stream's
are `registerPaymentDomain()` and `registerRefundDomain()`, and the pattern is
the same for A, B1, B2, D and F1. Each one installs the domain's ports and its
effect handlers:

```ts
export function registerPaymentDomain(): void {
  registerPaymentPort({ ensureNoOpenAttempts });
  registerPaymentEffects();
}
```

Nothing calls any of them. A grep across `apps/` finds no call site at all, in
either application, for any domain.

Two consequences, both silent at build time and both fatal at runtime:

**1. Ports throw.** `slot.get()` throws `INTERNAL` with `"… 尚未注册（拥有该端口的
stream 未加载）"`. So `resolveStockPort()` in a checkout, and
`resolvePaymentPort()` in a cancel, fail on the first real request. The port
slots are last-write-wins and have no other initialisation path, so the only
reason the suites are green is that every integration test registers its own
fakes in `beforeEach`.

**2. Effects are parked, permanently.** `system.dispatchEffects` runs every five
seconds. When it claims a row whose scope/eventType has no handler, it does not
skip it and try again later — it settles it:

```ts
await settleFailure(ctx.db, effect, `no handler for ${row.scope}/${row.eventType}`, …)
```

which parks the row as `unknown`. There is no un-park (`CR-4-c`). So the first
dispatcher pass after boot destroys whatever the ledger is holding. For this
stream that is `refund.execute`, the effect that moves money: a refund approved
just before a deploy would be marked as permanently un-runnable, with the buyer
waiting and nothing on any screen saying why.

This is the sharpest edge in the whole seam design. The registry exists so that
domains can be wired at the edge instead of importing each other — and the edge
is empty.

## Asked for

A gen'd bucket, in the same spirit as `jobs.gen.ts`, `routes.gen.ts` and
`menu.gen.ts`, so that adding a domain never means editing a shared file:

```ts
// packages/core/src/domains.gen.ts — generated by `pnpm gen`
import { registerCatalogDomain } from "./catalog";
import { registerOrderDomain } from "./order";
import { registerPaymentDomain } from "./payment";
import { registerRefundDomain } from "./refund";
// …

/** Idempotent, last-write-wins. Safe to call more than once. */
export function registerAllDomains(): void {
  registerCatalogDomain();
  registerOrderDomain();
  registerPaymentDomain();
  registerRefundDomain();
}
```

discovered by the same convention the other buckets use — an exported
`register<Name>Domain` in `core/src/<domain>/index.ts` — and called from exactly
two places: `buildWorkerContainer()` and the web app's container, both before
anything can serve a request or claim an effect.

Order must not matter. It does not today: every registration is a `Map.set` or a
slot assignment, and no domain reads another's port at registration time. Worth
stating in the generated file's comment so it stays true.

While this is open, `system.dispatchEffects` should arguably _skip_ an
unhandled effect rather than park it — a handler that does not exist yet is not
the same fact as a handler that failed. That is a smaller change than this one
and would turn a data-loss bug into a log line.

## Meanwhile

The four job modules this stream owns call their domain's registration at
**module scope**, not in the handler:

```ts
registerPaymentDomain();
```

`jobs.gen.ts` imports every job module at boot, so the handlers exist before the
first dispatcher pass — which is the whole reason it is at import and not in the
handler, where a few seconds of every deploy would park live rows.

It covers the worker and nothing else. The **web app is still unregistered**, so
B1's cancel route sees no `PaymentPort` and falls back to
`"no PaymentPort registered; treating payment as closed"` — a debug log and a
cancel that skips the payment guard entirely. That is the failure this CR is
most urgent about, and no path inside this stream's ownership can fix it.
