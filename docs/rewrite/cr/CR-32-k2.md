# CR-32-k2 — the header bell never shows a notification

**Stream:** K2 (hardening second pass) **Status:** OPEN — for the orchestrator (P0-b's hook, N1's route; both merged)
**Found by:** `next/e2e/admin/specs/notification.spec.ts` (two `test.fail` cases name this CR)
**Files:** `next/apps/web/app/admin-api/notifications/stream/route.ts`,
`next/apps/web/src/admin/notifications/use-notification-stream.ts`,
`next/apps/web/src/admin/notifications/notification-bell.tsx`

## What

Two defects, one symptom: an admin never sees a notification in the bell.

1. **Named events, unnamed listener.** The SSE route writes
   `event: notification\ndata: …\n\n`. The hook only sets `source.onmessage`,
   and `onmessage` fires for events **without** an `event:` field. A named
   event is delivered to `addEventListener('notification', …)` and to nothing
   else. The spec proves both halves in a real browser: an `EventSource` on
   the same URL receives the push as a named `notification` event whose
   payload parses as `adminNotification`, and never as an unnamed message.
2. **The inbox is never read.** N1 wrote a durable inbox —
   `GET /admin-api/notifications`, `/unread-count`, `POST /:id/read`,
   `/read-all` — and no admin screen calls any of them. The bell starts empty
   on every page load, so a notification pushed while the operator was on
   another tab, or before they signed in, is never seen. "Mark read" and
   "全部已读" change local state only; the next reload brings nothing back
   because nothing was ever loaded.

## Asked for

1. In `use-notification-stream.ts`, listen for the event the server sends:
   `source.addEventListener('notification', handler)` (keep `onmessage` only
   if an unnamed event is ever meant to exist). Or drop the `event:` line
   from the route — but the hook is the smaller change and the named event is
   the better protocol.
2. Seed the bell from `notificationAdminInboxList` (`unreadOnly`) and
   `notificationAdminUnreadCount` through `callRoute` on mount, and make
   `markRead` / `markAllRead` call `notificationAdminMarkRead` /
   `notificationAdminMarkAllRead`. The push then only prepends to a list that
   already holds the unread rows; the SSE payload's `id` is the inbox row's
   id, so de-duplication already works.

## Done when

Both `test.fail` cases in `notification.spec.ts` ("the bell shows a pushed
notification", "the bell shows the unread inbox on load") start passing —
Playwright reports them as unexpected passes — and the `test.fail` lines are
deleted.
