## Load order

`system, config, storage, user, shipping, catalog, groupbuy, presale, coupon,
cms, diy, wechat-oa, notification`

Two groups moved, and both are foreign-key reasons:

- **`shipping` now loads before `catalog`.** `products.shipping_template_id`
  restricts `shipping_templates`, and catalog keeps a product's template only
  if shipping loaded it (a soft dependency). The same holds for the activity
  tables.
- **`groupbuy` and `presale` load right after `catalog`.** An activity restricts
  `products`, an activity SKU restricts `product_skus`, and both may name a
  `shipping_templates` row.

`cms` stays after catalog because an article may link a product. `wechat-oa` and
`notification` come last: they only point at users and admins.

## The runner: one transaction per run

A full run is now **one PostgreSQL transaction**. Before any group loads, it
clears every selected group's targets in reverse load order, across groups.
Groups then load in order. Any failure, or the dry-run marker, rolls everything
back.

The old per-group clear could not rerun. Restricting FKs from later groups
(`products → shipping_templates`, `groupbuy_*`/`presale_* → products,
product_skus, shipping_templates`) refuse the `DELETE`. `--group X` still clears
only X.

A group that fails now fails the run with `整次迁移的事务已回滚，目标库保持原样`.
There is a test for this: `一个 group 失败，整次迁移回滚，目标库保持原样`.

**Seeded dictionaries are upsert targets** (`TargetSpec.upsert`), never
cleared:

- `express_companies` by `id`;
- `notification_templates` by `code`.

On conflict every carried column is overwritten except the key and `created_at`.

The runner's `GroupContext` gained two hooks for the activity groups:

- `selectTarget(table, columns)` reads rows this run already loaded, inside the
  transaction (the catalogue SKUs);
- `countSource(table, where?)` returns 0 when the dump lacks the table (legacy
  teams and presale orders).

## `etl verify`: every group has a rule

**Row counts.** New rules, with the existing ones for system, storage, catalog,
coupon, diy and config kept:

- **user:**
  - `users` exact (cancelled accounts migrate);
  - `user_addresses` exact against `uid in (select uid from eb_user)`;
  - `user_labels` and `wechat_identities` at most.
- **shipping:** `shipping_templates` exact.
- **cms:**
  - `article_categories` and `articles` exact;
  - `article_contents` exact against `nid in (select id from eb_article)`.
- **wechat-oa:**
  - categories exact;
  - `wechat_qrcodes` exact against codes that have a ticket in `eb_qrcode`;
  - scans exact against scans of those codes;
  - auto replies at most `eb_wechat_key`;
  - media at most the rows with a `media_id`.
- **notification:** messages at most `is_del = 0`.
- **groupbuy:**
  - activities exact against `is_del = 0 and people >= 2 and product_id in (select id from eb_store_product)`;
  - SKUs at most `type = 3`.
- **presale:**
  - activities exact against `is_del = 0 and product_id in (…)`;
  - SKUs at most `type = 6`.

**Money sums:**

- `groupbuy_activities.price` and `presale_activities.price` against the same
  filters (new);
- coupon, SKU and product prices (as before).

**Structure**, where a count cannot see the invariant:

- `shipping:fallback`: every template has exactly one fallback rule.
- `shipping:express`: every legacy courier's code, sort order and switch landed
  on its id, or its code is held by another seeded id and was left to the seed.
- `wechat:scene`: every QR code's `scene` equals its legacy id, so printed
  posters keep attributing.
- `notification:templates`: every legacy template the registry knows is present
  under its new code with the legacy name and audience.

**Why no money sum:**

- **shipping** has prices but regroups them. One legacy row per city becomes one
  rule per set of cities, so a total is not an invariant. The fallback check is
  what must hold instead.
- **system, config, storage, user, cms, diy, wechat-oa, notification** have no
  money.

**`--full-digest`** applies to storage only (the only group with files), as
before. The drill runs verify with it.
