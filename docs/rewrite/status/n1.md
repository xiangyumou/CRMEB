## Decisions

1. **How the origin is sourced: a zod default that reads the environment.**
   `publicOrigin: z.string().max(255).default(() => originFromEnv())`, with no
   `ui` entry and no `legacyKeys`.

   The alternatives were a `packages/db` seed row and a write from the web/worker
   bootstrap. Both make the value a *copy* of a deployment fact, which then goes
   stale the day the shop moves domain and nobody re-runs the seed — the failure
   CR-1-e2 exists to stop. A function default is read on every `config.get`, so
   the environment is the single source of truth, there is no migration, and a
   shop that does set a row (the ETL, say) still wins over an unset variable.

2. **The variable is `PUBLIC_ORIGIN`, falling back to `APP_ORIGIN`.** The CR
   names `PUBLIC_ORIGIN`; `apps/web/src/server/env.ts` already requires
   `APP_ORIGIN` of every deployment for the CSRF `Origin` check, described there
   as "Site origin, used for the CSRF `Origin` check and for absolute URLs" —
   the same fact under an older name. Honouring both means no running shop needs
   a new variable. `extraOrigins` reads `EXTRA_ALLOWED_ORIGINS`, which env.ts
   already parses for the same purpose, so a staging domain is listed once.
   *If the orchestrator wants one name only, deleting the `APP_ORIGIN` fallback
   is a one-line change.*

3. **Read-only is by omission, not by a flag.** `ConfigFieldUi` has `secret` but
   no `readOnly`, and `ConfigFieldDescriptor` is a contract
   (`@shop/contracts/system/schemas`) this stream may not change. A field with no
   `ui` entry is already the kit's documented way of saying "not an operator
   setting" (`config.service.ts`: "A key with no `ui` entry is deliberately not
   editable in the admin"), so both fields have none. **Cost:** the CR also asked
   that "the config screen shows the value and where it came from", and that part
   is *not* done — the screen does not render the field at all. It needs a
   `readOnly` kind in the descriptor, which is F1 + contracts work.

   Related gap, left alone deliberately: `configSave` validates keys against
   `schema.shape`, not against `ui`, so a hand-crafted `PUT` from an admin
   holding `system:config:write` can still store a ui-less key. Two such keys
   already exist (`payment.apiBaseUrl`, `wechat.apiBaseUrl`), so tightening it is
   a behaviour change for other groups and belongs in a CR, not here.

4. **`wechat-oa`'s JS-SDK signer got the smallest possible swap.**
   `jssdkConfigFor` now reads `publicOrigin(ctx)` where it read
   `notification.siteBaseUrl`; its local `assertAllowed` is otherwise untouched
   and still layers the operator-editable `wechat-oa-runtime.jsApiAllowedHosts`
   on top. `isTrustedHost` is exported and tested but has no caller yet — E3
   owns that endpoint and collapses the two.

   This also means nothing was lost by making `site.extraOrigins` non-editable:
   the operator-facing list of 公众号 JS 安全域名 stays where it belongs, in
   `wechat-oa-runtime`, which is a statement about the WeChat account rather than
   about this deployment.

5. **Option B, as the CR says: `notify(tx, ctx, …)` inline, no hook registry.**
   Each call is the last thing the business transaction does, after the row it
   is about exists and after the status log, so a notification can never
   describe a state the database does not hold. NOTIF-001 still applies in the
   other direction: `notify` swallows an unknown event code and the ledger
   swallows a repeat, so no call site can fail the change it announces.

6. **`order_price_changed` carries the new amount in its subject.**
   `order-price:<orderId>:<payableAmount>`, not `order:<orderId>`. 改价 is
   *additive* and repeatable — the operator can discount 20 元 now and 10 元 an
   hour later — and a per-order key would record the first change and silently
   swallow every one after it. This is the CR's own rule for two partial refunds
   of one order, applied to the same shape of problem. An adjustment that
   changes nothing (a 0.00 discount) is still one subject and is deduplicated,
   which is right: the shopper is told once that the price is 40.00.

7. **`StockPort.reserve` takes `ctx` as an optional trailing parameter.**
   The port's fakes live in `packages/testing`, which this stream may not touch,
   and ~20 test call sites pass three arguments. A trailing optional parameter
   keeps every one of them structurally assignable while letting B1 hand the
   catalog what 库存预警 needs. The alternative — `(tx, ctx, orderId, lines)`, to
   match the kit's usual argument order — is the tidier signature and the right
   follow-up once the fakes can move.

8. **`installNotificationHooks()` no longer runs at module scope.**
   `notification.effects.ts` called it on import. Once `order` imported
   `notification` (it must, to call `notify`), that closed the cycle
   `order/index → order.checkout.service → notification/index →
   notification.effects → ../order`, and the hook install ran while `../order`
   was still evaluating: `registerFulfilmentNotifier is not a function`, the
   cdc04601d class of bug. The install now happens only in
   `registerNotificationDomain()`, which is what `@shop/core/domains` calls at
   bootstrap and what the notification integration suite already called.
   `registerEffectHandler` stays at module scope; it has no cross-domain import.

9. **Test-only: the catalog integration suite invalidates the config cache.**
   `truncateAll` empties `settings` but not Redis, and `config.set` reads the
   *cached* current values to decide which keys changed — so a stale cached
   value equal to the one being set makes the write a no-op and leaves the group
   on its schema defaults. `groupbuy.int.test.ts` already carried the same line
   for the same reason; this is not a production bug (nothing truncates
   `settings` under a live cache) but it is a sharp edge worth knowing about.
