## Routes added, field by field — for H2/H3

Nothing under `template/uni-app` was touched; every marker below is H2's to
delete. `pnpm guards`' `uniapp` check now lists them as **pending(H2)** rather
than failing (CR-1-e4).

### `POST /api/v1/auth/phone/wechat-mini` — `auth: 'user'`, 200

Body `{ phoneCode }` (1–512 chars, the `getPhoneNumber` code). Response
`{ ok: true }`. Errors: `AUTH_WECHAT_NOT_CONFIGURED` (409),
`AUTH_WECHAT_CODE_INVALID` (422), `AUTH_PHONE_TAKEN` (409),
`AUTH_PHONE_ALREADY_BOUND` (409). Marker: `mpBindingPhone` in `api/user.js`.

### `GET /api/v1/wechat/mini-qrcodes` — `auth: 'user'`, 200

Query `{ page, scene }`. `page` must be one of four:
`pages/index/index`, `pages/goods_details/index`,
`pages/activity/goods_combination_details/index`,
`pages/activity/presell_details/index`. `scene` is 1–32 characters from
`[0-9a-zA-Z!#$&'()*+,/:;=?@\-._~]`, which is what WeChat documents as safe; the
**32-byte** limit WeChat actually enforces is checked in the domain, where the
encoding is known, so `id=一二三四…` is refused here rather than at WeChat with
a number nobody can read. Response `{ url }`. Error
`WECHAT_MINI_CODE_FAILED` (502).

### The six staff routes — `auth: 'staff'`

All six take a staff session (a shopper bearer token whose user id is in
`order_notice_admin_uids`); a shopper who is not on the list gets 403.

| Route | Query / body | Response |
| ----- | ------------ | -------- |
| `GET /api/v1/staff/users` | `page`, `pageSize`, `keyword?`, `groupId?`, `labelId?` | `{ items, total, page, pageSize }` |
| `GET /api/v1/staff/users/:uid` | — | one item, the same shape |
| `GET /api/v1/staff/user-groups` | — | `{ items: [{ id, name }] }`, unpaginated |
| `POST /api/v1/staff/users/:uid/group` | `{ groupId: string \| null }` | one item |
| `GET /api/v1/staff/users/:uid/labels` | — | `{ categories: [{ categoryId, categoryName, labels: [{ id, name, assigned }] }] }` |
| `POST /api/v1/staff/users/:uid/labels` | `{ labelIds: string[] }` (≤ 50) | one item |

**The item** — the same shape for the list and the detail, ten fields:

```
id           string
nickname     string | null
avatarUrl    string | null
phone        string | null   masked, always: 138****8000
status        'active' | 'disabled'
groups       [{ id, name }]
labels       [{ id, name }]
orderCount   number | null   null = unknown, render 「--」
spendTotal   string | null   "3980.00"; null with orderCount
createdAt    ISO-8601 with offset
```

Errors: `USER_NOT_FOUND` (404) on all five that name a `:uid`,
`USER_GROUP_NOT_FOUND` / `USER_LABEL_NOT_FOUND` (404) on the two writes.

**Three things H3 has to change in `api/admin.js`** — the wrappers there were
written against CR-2-h2's sketch, not against what landed:

1. `postUserSetLabel` (`api/admin.js:369`) sends `{ labelId: String(labelId) }`.
   It must send `{ labelIds: [...] }`, an array of id strings. Its one caller,
   `components/userLable/index.vue:79`, **already passes an array**, so today
   the wrapper stringifies it into `"[object Object],[object Object]"`.
2. `getUserLabel(0)` passes a literal `0` as the uid, at
   `components/userLable/index.vue:106` and `components/filter/index.vue:99`.
   `:uid` is a real customer id (`/^[1-9]\d*$/`) and `0` is a 422 — pass the uid
   whose drawer is open. The response's `assigned` flag then replaces the
   component's own `inArray(label.id, this.dataLabel)` bookkeeping, and the
   filter screen, which only wants the catalogue, can read it off any uid it
   already has.
3. `postUserSetGroup` (`api/admin.js:353`) sends `{ groupId: String(groupId) }`,
   which turns a null into the string `"null"` and a 422. The route accepts
   `{ groupId: null }` to clear the group (未分组) and the picker should offer
   that option, so the null has to survive the wrapper.

Also note the field names are camelCase and the legacy ones are not: the
component reads `item.label`, `j.label_name`, `infoData.group_id`,
`data.label_id`. The new shapes are `categories[].labels[]`, `.name`,
`groups[0].id` and `labels[].id`.

### `POST /api/v1/visits` — `auth: 'user-optional'`, **204**, empty body

Body `{ path, platform? }`. `path` is a storefront route beginning with `/`,
≤ 255 chars, **no query string and no fragment** (`/^\/[^?#\s]*$/`) — a path
carrying one is a 422. `platform` is `h5` | `wechat-oa` | `wechat-mini` and
defaults to whatever `X-Client-Platform` said. No response body, no errors
other than the 422.

## The SMS limits, as they actually are (§2)

Every one of these is a config field an operator can change; the numbers are
the defaults. Two config groups are involved, which is why the brief asked for
them to be written down in one place.

| Limit | Key | Default | Bounds | Where |
| ----- | --- | ------- | ------ | ----- |
| Code lifetime | `storefront-auth.codeTtlSec` | 300 s | 60–1800 | `storefront-auth.config.ts` |
| Resend cooldown, per phone **per scene** | `storefront-auth.codeResendSec` | 60 s | 30–600 | same |
| Wrong guesses a code survives | `storefront-auth.codeMaxAttempts` | 5 | 3–10 | same |
| Codes per source address per day | `storefront-auth.codePerIpPerDay` | 50 | **10**–1000 | same |
| Codes per phone per hour | `sms.perPhonePerHour` | 5 | 1–50 | `system/sms.config.ts` |
| Codes per phone per day | `sms.perPhonePerDay` | 20 | 1–200 | same |

Counters: `sms:budget:hour:<phone>`, `sms:budget:day:<phone>`,
`sms:budget:ip:<ip>`, and the resend window keyed on phone **and** scene.
A code is destroyed on use and on the `codeMaxAttempts`-th wrong guess, and a
code minted for one scene does not work in another.

The per-IP floor of **10** is worth remembering: a test that wants to prove the
budget cannot ask for a limit below it — `codePerIpPerDay: 3` is a
`VALIDATION_FAILED` from the config schema, not a throttle.

### Decision: no behaviour captcha (CR-2-h2 §1)

`getAjcaptcha` / `ajcaptchaCheck` stay unimplemented. The seam exists — an
`CaptchaVerifier` registered through `registerCaptchaVerifier` is asked on
**every** SMS request (not after N failures, because an SMS costs money on the
first one) — and nothing registers one. The reasons:

- the legacy 滑块 was a client-side puzzle whose answer the client checked; it
  stopped nobody and cost a round trip on every 登录 screen;
- the budgets above are what actually bounds the spend, and they bound it per
  phone and per address whether or not a puzzle was solved;
- a real captcha is a third-party dependency with its own credentials, its own
  outage mode and its own privacy story, and choosing one is not a decision a
  rewrite stream should make on its own.

If one is ever wanted, `registerCaptchaVerifier(impl)` is the whole change on
this side, and `AUTH_CAPTCHA_REQUIRED` / `AUTH_CAPTCHA_INVALID` already exist.

## Decisions

- **What a 店员 may see** (§4). An allow-list, not the console's shape minus a
  few fields. `account` is excluded because for a phone-registered customer it
  *is* the phone number and would undo the mask; so are `realName`, `birthday`,
  `registerIp`, `lastLoginIp`, `adminRemark`, `addressCount`, the address book,
  `boundWechat` and `hasPassword`. There is no unmasked phone on any staff
  route, including the detail one, where the console does hand one out.
- **The staff keyword search is narrow** (§4). Nickname as a substring, phone
  only as the whole eleven digits. `ilike '%1380%'` over a column the same
  screen masks is a way to walk the customer base four digits at a time from a
  shared handset. `repo.AdminListFilters` gained `keywordMatch: 'console' |
  'staff-narrow'` for this; the console's behaviour is unchanged.
- **`{ labelIds }`, not `{ labelId }`** (§4). The drawer submits its whole
  selection on 确定 and a singular field cannot express 取消. 分组 stays
  singular because the screen above it is a radio picker.
- **`orderCount` / `spendTotal` are `null` until the order stream registers a
  port** (§4, CR-2-e4). `user.repo.ts` may not read the order tables and the
  rule for which orders count lives in the order aggregate. `null` rather than
  `0`, because `0` would call a customer with forty orders a first-time buyer,
  and rather than a 500, which would take down the 用户 screen over two
  decorative numbers.
- **The mini-code cache resolves its own race** (§5). `onConflictDoNothing`
  plus a re-read, and the loser deletes the file it uploaded — proven by
  `wechat.mini-code.concurrency.int.test.ts`, which asserts one row, one URL
  and exactly one file in shared storage.
- **A WeChat refusal is never cached** (§5). `wxa/getwxacodeunlimit` answers
  200 with a JSON body on failure, so the client decides file-vs-refusal on the
  content type and `sniffFileType` must agree it is an image before anything is
  stored. A client that trusted the status line would serve a broken PNG for
  ever.
- **All WeChat credentials belong to the `wechat` group** (§7, CR-1-j).
  `wechat-mini` keeps only `enabled`, `name`, `contactType`, `contactPhone`.
  `token` / `encodingAesKey` / `messageMode` moved to `wechat` as `miniToken` /
  `miniAesKey` / `miniMessageMode` with their legacy keys. `wechat_token` and
  `wechat_encodingaeskey` were **dropped** from `wechat`'s `legacyKeys` rather
  than duplicated: they belong to F1's `wechat-oa` group alone (CR-3-e2).
- **The ETL "no legacy key has two claimants" assertion is scoped** (§7). It
  is impossible to state absolutely on the live registry without editing other
  streams' config groups: five genuine duplicates predate this stream
  (`store_stock`, `system_delivery_time`, `system_comment_time`,
  `order_notice_admin_uids`, `site_url`). The test asserts an exact table of
  those five plus an absolute rule that no `wechat_*` / `routine_*` key has two
  claimants. Ledger row ETL-J-009 was repointed at the renamed tests.
- **The 409 on a duplicate category name no longer hedges** (§8). With the
  index scoped to `deleted_at is null`, 该分类名称已被占用 is simply true;
  the old message had to add 「也可能属于一个已删除的分类」 because a name the
  operator deleted last month stayed taken by a row nothing on screen showed.

## Deviations, and why

- **The visits beacon has no `session_id` and no `city`** (§6). The brief's
  column list is CR-1-f3's, and `user_visits` as F3 actually built it has
  neither column — it has `id, user_id, path, platform, ip, province, stay_ms,
  created_at`. This stream was granted one migration (`wechat_mini_codes`) and
  altering another stream's table for two columns nothing yet reads was not
  worth the merge risk. Consequences:
  - the per-minute throttle is keyed on `coalesce(user_id, ip)`, which is the
    identity `stats` already counts 访客数 by, rather than on a session id. A
    client-supplied `X-Session-Id` would have been worse: it is the one value a
    caller can randomise, so it would turn the throttle off for anyone who
    tried;
  - `province` is written `null` and `city` does not exist. `stats` buckets a
    null province as 未知, so 地域分布 degrades rather than lying. A geo source
    remains unbuilt.
- **`@shop/testing` was edited outside §1's move** (CR-3-e4). Adding routes
  made `packages/testing`'s unit suite fail on `/api/v1/addresses/default`, a
  route E4 never touched: the mock server's specificity comparator was not a
  total order, so `Array.prototype.sort` could place a `:param` route ahead of
  the literal one it shadows, and *which* route broke depended on how many
  routes existed. Fixed by comparing derived keys, with an invariant test over
  the whole table. The next stream to add a route would have hit it.
- **`packages/core/src/payment/payment.config.test.ts` was edited** (§7). It
  pins the `wechat` group's secret fields by name, so adding `miniToken` /
  `miniAesKey` required adding them there. One list, one comment.
- **`next/guards/src/checks/uniapp.ts` was changed** (CR-1-e4). Landing a
  contract whose uni-app call still carries a `CONTRACT-PENDING(<merged
  stream>)` marker turned a pending H2 item into a hard failure that no stream
  in flight is allowed to fix (`template/**` is out of scope and off-limits).
  A call already on `MARKER_REASSIGNMENTS` now yields `pending(H2)` instead of
  `fail`; an unlisted stale marker still fails.
