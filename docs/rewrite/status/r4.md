### CR-8-k — an admin session kept alive past 32 h survived a password change

- **Commit:** `e3da5bed2` — **RESOLVED**

- **Change:** `core/auth/admin-session.store.ts` — `resolve()` runs one Lua
  script: `PEXPIRE` the session, and only if it still exists, `SADD` it back
  into the per-admin index and `PEXPIRE` the index to `ttl × 4`. The index can
  no longer expire under a live session, and a session whose index lapsed
  before the fix is re-listed on its next request. The misleading "second
  belt" comment is gone.
- **Tests:** flipped `auth/admin-session.revoke.int.test.ts::K-SEC-A1 — revoking every session of an admin > reaches a session that has been kept alive past four TTLs`;
  added `… > re-lists a live session whose index has already expired, so the next revoke reaches it`.
- **Left:** fix (2), an absolute session lifetime, is not built — a product
  question (it costs a working admin one login a day), no longer needed for
  correctness.

### CR-9-k — audit redaction was one level deep

- **Commit:** `1bcffc08d` — **RESOLVED**

- **Change:** `core/auth/audit.repo.ts` — `redactPayload` walks objects and
  arrays to depth 8 (deeper becomes `[truncated]`). A key is replaced when it
  is on the backstop list (now case-insensitive), matches a credential-shaped

  `handle()` because the registry is global and the over-redaction (a
  same-named non-secret field elsewhere) is harmless in an audit row.
- **Tests:** flipped `auth/audit.redact.test.ts::K-SEC-U12 — what the operation log keeps of a request body > redacts the same credential one level down, as the config form sends it`;
  added four unit cases (arrays/depth, case and shape, registry-driven, depth

### CR-12-k2 — admin login outcomes are recorded

- **Commit:** `2c51d87ae` — **RESOLVED**

- **Change:** `core/auth/admin-auth.service.ts` — `login(ctx, input, meta?)`
  wraps the old body (now `attempt`) and writes one `audit_logs` row per
  outcome: `routeId: 'auth.adminLogin'`, `POST /admin-api/auth/login`, the
  status the caller got, `adminAccount` = the typed account, `adminId` (and
  `target: admin:<id>`) once the account is known, `ip` = `meta.ip`, and a
  payload of `{account, result, code?, userAgent}` — never the body. Results:
  `success`, `invalid_credentials`, `locked`, `disabled`, `captcha_failed`
  (required or invalid), `error`. A failed write is logged and swallowed.
  `app/admin-api/auth/login/route.ts` passes `requestMeta(ctx.request)` from
  `app/api/v1/auth/_request.ts`, i.e. `clientIp()` (R3 owns what that reads).
- **Tests:** flipped `auth/admin-login.trail.int.test.ts::K-SEC-A4 — what a password-guessing run leaves behind > leaves a readable trail of the failed attempts, without the password`;
  added `… > writes one row per outcome, naming the account, the result and the address`
  and `… > records a disabled account after the right password, as disabled`.
  `apps/web/src/server/handle.int.test.ts`: `does NOT audit the login itself — the body holds the password`
  became `records the login outcome, never its body — the service writes it, not handle() (CR-12-k2)`
  (not a ledger id).
- **Knock-on (outside ownership, test-only):** eleven admin route test files
  log in through the real route and then count `audit_logs`; each such read
  now filters out `auth.adminLogin` rows (one expression per site, with a

### CR-15-k2 — the SSE stream outlived its session; a Redis connection per tab

- **Commit:** `a6c9cc5ec` — **RESOLVED**

- **Change:** `core/notification/notification.stream.ts` — `subscribeToAdmin`
  goes through a per-process hub: one `redis.duplicate()` subscriber shared by
  every stream, channels reference-counted (SUBSCRIBE on the first listener,
  UNSUBSCRIBE on the last, connection dropped when no stream is left), and
  `AdminStreamLimitError` past `MAX_STREAMS_PER_ADMIN` = 8 per admin per
  process (`openAdminStreams()` for probes). `core/auth` gains
  `AdminSessionStore.peek` / `AdminAuthService.peek` — a read that does **not**
  slide the TTL, so an open tab does not keep an idle admin signed in. The
  route (`app/admin-api/notifications/stream/route.ts`) still resolves the
  cookie itself (the guards' bare-handler rule) and hands off to
  `_stream.ts::serveAdminNotificationStream`, which subscribes before
  answering (429 `RATE_LIMITED` over the cap — final for an `EventSource`),
  and on every 25 s keep-alive peeks the session and closes the stream when it
  is gone or names another admin.
- **Tests:** new `apps/web/app/admin-api/notifications/stream/stream.int.test.ts`
  (6): forwards a named event and keeps alive; **closes on the next tick once
  every session is revoked**; does not slide the session; three streams cost

  notification suite (21) passes on the hub unchanged.
- **Left:** the cap is per process, not a Redis counter across replicas —
