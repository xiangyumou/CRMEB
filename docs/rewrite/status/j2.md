  `_next/static`, and the H5 history fallback last.

### Why the worker image is built twice over

The brief asks for the `pnpm deploy --prod` versus esbuild decision on the
record. It is **both**, and neither alone would work:

- `@shop/*` packages publish **TypeScript source**, not build output. A
  `pnpm deploy --prod` tree therefore contains `.ts` files the runtime cannot
  execute — so the first-party code is bundled with tsup/esbuild
  (`noExternal: [/^@shop\//]`).
- The third-party dependencies that must not be bundled — `pg`, `pg-native`,
  `ioredis`, `bullmq` — have native bindings or do their own dynamic requires.
  They come from `pnpm deploy --filter @shop/worker --prod --legacy`, whose
  `node_modules` is 56 MB. Bundling them instead would be smaller and would
  break in ways that only appear under load.

So: esbuild for our code, the package manager for theirs, and
`rm -rf /deploy/node_modules/@shop` afterwards so the source copies cannot
shadow the bundle.

`docker/worker/tsup.config.ts` **imports** `apps/worker/tsup.config.ts` rather
than restating it, so the externals list cannot drift between the two. It adds
`packages/db`'s migrator and seed as extra entries that keep their source
directory shape, because `migrate.ts` resolves `../migrations` and
`seed/reference-data.ts` resolves `../../seed-data` from `import.meta` at
runtime. Verified in the built image that those two entries did not get hoisted
into a shared chunk. That is what lets the `migrate` one-shot be the worker
image with a different command instead of a second 280 MB image.

### The stack — `deploy/next/`

| File | What it is |
|---|---|
| `compose.yml` | the stack: postgres, redis, migrate (profile), web, worker, edge |
| `compose.traefik.yml` | the traffic switch — labels *and* the external network, in one deliberate file |
| `deployment.env.example` | the template; `deployment.env` itself is gitignored and holds the two passwords |
| `lib/common.sh` | compose wiring, settings, digest capture, `psql` inside the container |
| `lib/readiness.sh` | the readiness gate |
| `upgrade.sh` | deploy a release, end on the previous digests if it does not come up |
| `rollback.sh` | return to known digests; `--restore` for data, never implied |
| `backup.sh` | dump and prove it restorable; `--verify-only` for an existing dump |
| `readyz.sh` | the gate on its own, read-only |
| `rehearsal/` | the drill, and the two deliberately broken candidates it uses |
| `cutover.md` | the one-time switch from the old stack (PLAN §6) |
| `README.md` | the recipes and the rules |

Rules the scripts keep, and the reason each one is there:

- **Digests only.** `upgrade.sh` refuses a moving tag. A tag can be repointed
  between the run that passed acceptance and the deploy, which makes the
  rollback target unidentifiable.
- **All three roles, every release.** A release where `web` moved and `worker`
  did not is a web talking to a worker built against a different contract.
- **No credential in argv.** Every password is expanded by the shell *inside*
  the container that needs it, so nothing lands in `/proc/*/cmdline`.
- **Pull before stopping a writer**, so a registry problem is not discovered
  mid-window.
- **Back up, and prove the backup**, before the first migration.
- **`down -v` is never run** against a real project. The only occurrence in the
  directory is in the drill's teardown, against a literal project name.

## Memory budget

The host is 2 cores / 3.6 GB and runs the old stack too. Caps are cgroup limits
from `compose.yml`; usage is `docker stats` against the drill stack with the
seed loaded and no traffic.

| Service | Cap | Idle | Heap cap |
|---|---|---|---|
| postgres | 512 MiB | 94 MiB | — (`shared_buffers=128MB`, `max_connections=40`) |
| redis | 160 MiB | 20 MiB | — (`maxmemory 96mb`, `noeviction`) |
| web | 512 MiB | 143 MiB | `--max-old-space-size=384` |
| worker | 320 MiB | 58 MiB | `--max-old-space-size=224` |
| edge | 64 MiB | 24 MiB | — |
| **total** | **1568 MiB** | **339 MiB** | |
| `migrate` | 384 MiB | one-shot | `--max-old-space-size=288` |

`migrate` runs under a profile while `web` and `worker` are stopped, so its 384
reuses their 832 rather than adding to the total. Under the brief's 1.6 GB
ceiling with 32 MiB to spare — deliberately tight, because the old stack is
still running during cutover.

The explicit `--max-old-space-size` on every node service is not tuning. V8
sizes its heap from the **host's** memory, not the cgroup's, so a container
without one grows past its limit and is OOM killed with no diagnostic at all.

## The drill — `deploy/next/rehearsal/drill.sh`

One command that builds the three images, starts a throwaway registry, pushes
them for real digests, and then deploys, fails and rolls back a real stack.
Case ids are stable so `invariants.md` can cite them (CR-2-j2). It runs in its
own Compose project against generated passwords in `$TMPDIR`, so it can run
beside a live stack — including on the production host, where rehearsing is the
point.

```
$ deploy/next/rehearsal/drill.sh
```

**16 passed, 0 failed, 0 skipped** — about 25 minutes on this machine, most of
it spent bringing stacks up and tearing them down. The transcript, trimmed to

The three failing-release cases are what the brief asked for by name. Each one
ends with `deployment.env` **and** the running containers back on the previous
digests — the drill checks both every time, because a rollback that edited the
file and left the old container up, or restarted the container and left the
file pointing at the failed release, surprises the next person to run
`docker compose up`. The manifest records
`outcome=rolled-back reason=… migrated=1`, and `readyz.sh` passes afterwards.

`upgrade/readiness-gate-ends-on-previous` is the one that keeps the gate
honest: every container is healthy and both probes answer, and the release is
refused anyway because a table it needs is missing. Without that case the gate
could be a no-op and nothing here would notice.

Proved along the way, from the first deploy: one migration applied and
`seeded cities=3939 express_companies=1101 agreements=4 notification_templates=17`;
`/healthz` returns `ok` with `X-Content-Type-Options: nosniff`; `/readyz`
returns `{"status":"ok",…}`; the worker heartbeat fresh
(`node /app/healthcheck.mjs` → `ok age=13254ms`, TTL 4× the interval).

No credential appears in this file, in the drill's output or in the repository.
The drill generates its two passwords per run into a mode-600 file under
`$TMPDIR` and deletes it on teardown; `static/no-secrets-in-repo` is the case
that keeps the repository side of that true.

Deliberate: the drill uses a **local registry** rather than
`NEXT_ALLOW_LOCAL_IMAGES=1`, so pinning, pulling and reading back the digest a
container is actually running are all exercised — those are three separate
mechanisms, and a rehearsal that skips them proves the scripts work in the one
mode production never uses.

The two broken candidates are chosen, not convenient:

- `broken-worker.Dockerfile` — a worker that starts, stays up, logs nothing
  alarming and does no work. A candidate that crashed outright would be caught
  by Docker with no healthcheck at all, so it would prove nothing about the
  probe.
- `broken-migrate.Dockerfile` — a failing migration and *nothing else* broken,
  so "the release ended on the previous digests with the dump intact" cannot
  pass for the wrong reason.

`relabel.Dockerfile` produces a second release that behaves identically and has
a different digest, because an "upgrade" from a digest to itself makes "it
ended on the previous digest" true no matter what the script did.

## What the rehearsal found

Four defects, all fixed in `4abb1c97e` and later:

1. **The worker image crash-looped.** `CMD` pointed at `main.js`; tsup emits
   `.mjs` when the nearest `package.json` is not `type: module`, and there is
   no `package.json` at `/app`. Caught by the container healthcheck during the
   first rehearsal deploy — which is the healthcheck earning its place.
2. **The uploads volume came out root-owned**, so the uid-1000 web container
   could not write a single upload. A new named volume is seeded by whichever
   container mounts it first — **read-only mounts included** — and the edge won
   that race with nginx:alpine's root-owned directory. Fixed by `chown -R
   1000:1000 /data` in the edge image, so every image that declares the path
   agrees about who owns it.
3. **A first deploy that failed reported the wrong thing.** `roll_back()`
   returned 1 on `--first-deploy`, so the caller printed "THE ROLLBACK ALSO
   FAILED. The stack needs a human." and exited 3. There is no previous image
   on a first deploy; there is nothing to fail to roll back to.
4. **A dead `types { }` block** in the uploads location, immediately followed
   by `include mime.types` — a no-op dressed as a security control. Replaced
   with a real `include` plus `default_type application/octet-stream`.

And one found while writing the drill: `running_image_ref()` stripped a
registry port as if it were a tag (`127.0.0.1:15000/x` → `127.0.0.1`), so the
digest lookup silently fell back to the plain reference. Harmless against GHCR,
which has no port, and wrong.

Also confirmed by hand during the rehearsal, and not (yet) drill cases:
`/uploads/evil.php`, `evil.html` and `.secret` are 403; `ok.png` is served as
`image/png` and `note.bin` as `application/octet-stream`; a `../` traversal is
normalised by nginx into the SPA fallback and `%2e%2e` is a 400; both JS
containers report `uid=1000(node)`.
