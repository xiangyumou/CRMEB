### What other streams need from these contracts

1. **A session is a resource.** `POST /api/v1/auth/sessions/{password,sms,
wechat-mini,wechat-oa}` creates one, `DELETE /api/v1/auth/sessions/current`
   is 退出登录, `DELETE /api/v1/auth/sessions` is 退出所有设备. There is no
   `POST /auth/logout`.
2. **The token is in the body, not a cookie.** Storefront clients send
   `Authorization: Bearer <token>`. Only its sha256 is stored, and it carries
   the `password_version` it was minted with.
3. **WeChat sign-in answers with a flat two-state result**, not a union:
   `{ status: 'signed-in' | 'phone-required', session, registered, bindToken,
bindTokenExpiresInSec }`. `phone-required` hands back a short-lived
   `bindToken` so the second call does not have to redeem the (single-use)
   WeChat `code` again.
4. **`POST /api/v1/auth/sms-codes` takes a `scene`** (`login`, `register`,
   `reset-password`, `bind-phone`, `change-phone`). The scene is part of the
   Redis key, so a code minted to confirm a phone change cannot be replayed
   against login.
5. **The admin user-detail 订单 / 优惠券 tabs are other domains' routes.**
   `GET /admin-api/orders?userId=` (B2) and `GET /admin-api/user-coupons?userId=`
   (coupon). This stream ships only `GET /admin-api/users/:id/addresses`, and
   granting a coupon from the user page is coupon's own
   `POST /admin-api/coupons/:id/grants`.
6. **`phone` is masked in the admin list** (`138****8000`) and unmasked only on
   the detail route.

## Decisions

- **Contracts for storefront auth live in `contracts/src/auth/`**, not a new
  domain folder: `pnpm gen` aggregates exactly one `errors.ts` per domain
  directory, and splitting the auth surface in two would have meant two
  registries for one `AUTH_` prefix. `storefront-schemas.ts` keeps the two
  surfaces' shapes apart inside that folder.
- **SMS code login also registers.** A phone with no account gets one, and
  `registered: true` says so. The legacy funnel's 404 → "go and register with
  the same phone and the same code" step is the most abandoned in the old flow.
- **Rebinding a phone needs a code on the new number only.** Demanding one on
  the old number too locks out exactly the customers this screen exists for
  (lost or changed handset).
- **A password change accepts either proof**: the old password, or a fresh SMS
  code to the bound number. WeChat-created accounts have no password to quote,
  and the legacy system had no way for them ever to get one.
- **Address cap of 20 per customer.** The legacy system had none, which is how
  a scripted client filled the table. Recorded here because it is a new refusal
  (`USER_ADDRESS_LIMIT_REACHED`).
- **Group membership is many-to-many.** The schema's `user_groups_map` replaces
  `eb_user.group_id`; batch assignment therefore takes a `mode`
  (`replace` / `add` / `remove`), because the legacy `save_set_label` always
  replaced and silently stripped every other label from every selected
  customer.
- **Cancellation is a real two-step review.** The legacy storefront endpoint
  flipped `is_del = 1` immediately and the admin 同意/拒绝 endpoints were empty
  stubs that returned success. Approval here anonymises and revokes sessions;
  it never deletes a row that orders reference.

## Blocked / waiting

- **Stream C's WeChat client is not merged.** This stream defines a narrow
  `WechatIdentityPort` (`miniCodeToSession`, `miniPhoneNumber`, `oaCodeToUser`)
  inside `core/src/user/` with a fake for tests. **The orchestrator wires C's
  `WechatCoreClient` to it at merge**: `miniCodeToSession` → `miniCode2Session`,
  `oaCodeToUser` → `oaCodeExchange` + `oaUserInfo`. `miniPhoneNumber` has no
  method on C's client today and must go through `client.call('mini', { method:
'POST', path: '/wxa/business/getuserphonenumber', body: { code } })`.
