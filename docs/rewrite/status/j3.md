## Done

### 1. CR-1-j2 — `/api/v1/readyz`

Five files, as the CR lays them out.

| File | What it is |
| --- | --- |
| `contracts/src/health/errors.ts` | `HEALTH_NOT_READY` → 503 |
| `contracts/src/health/health.contract.ts` | `readinessPayload`, `storefrontReadiness` |
| `apps/web/src/server/health.ts` | the four checks |
| `apps/web/app/api/v1/readyz/route.ts` | `handle(storefrontReadiness, …)`, `force-dynamic` |
| `next/docker/edge/nginx.conf` | `location = /readyz` → `http://web/api/v1/readyz` |

Four checks, all four run concurrently under one 2 s budget: a database ping, a
Redis ping, **migrations applied**, and a **worker heartbeat** fresh within
`HEARTBEAT_INTERVAL_MS × 3`. A failure answers 503 with
`details.checks` and nothing else — no error text, no hostname, no connection
string. The int test asserts the 503 body by `toEqual`, so anything leaking
into it fails the build.

Two decisions worth recording:

- **The migration count is a constant in `health.ts`, pinned by a unit test**
  that reads `packages/db/migrations/meta/_journal.json` from disk. `@shop/web`
  has no Drizzle dependency (CONVENTIONS keeps Drizzle behind `*.repo.ts`), and
  the standalone bundle does not carry the migrations directory, so the journal
  cannot be read at runtime. The test fails the moment a migration is added
  without the constant moving, which is the only moment it matters.
- **The edge's container healthcheck was *not* pointed at `/readyz`.**
  CR-1-j2's compose change would have made the edge restart itself whenever
  PostgreSQL or Redis blipped — turning a degradation into an outage, which is
  the exact failure `health.ts` exists to refuse. The edge healthcheck is
  `/healthz && /api/v1/health`; `compose.yml` says so and why.

`deploy/next/lib/readiness.sh` now prefers `/readyz` over HTTP and keeps the
exec-based checks as the fallback for the window before the edge is up. It uses
`curl -w '%{http_code}'` from the host where curl exists, because busybox `wget`
inside the edge prints nothing on a non-2xx and the gate would lose the name of
the failing dependency.

release that would ship an empty shop says so rather than shipping quietly.

jobs, held to the same standard as the image job: the guards run inside the

count; the e2e job installs the browser *before* the suite and uploads its
report; and none of the three may publish anything. Four mutations of the
workflow were run against the guard and all four were caught.

### 3. CR-2-j2 — the OPS/REL invariant rows

The three J-owned tables replaced verbatim. **Zero `unmapped` rows** in the
three sections: OPS-002…013 and REL-001…007 are `ported`, OPS-001 is `retired`.

`tests/static/next-migration-guard.cjs` is new, and OPS-007 cites it: a drizzle
migration under `packages/db` containing `DROP TABLE`, `DROP COLUMN` or
`ALTER COLUMN … TYPE` fails the build unless that **statement** carries a
`-- destructive: approved` marker. Per statement, not per file: one line at the
top of a migration would bless everything added under it later. The condition is
the one `upgrade.sh`'s unattended rollback depends on.

REL-006/007 are `ported`, as the brief allows once §2's guard extension landed
in the same branch.

Making the new `Guards` step green needed two more edits, both of which are the
handoff CR-2-j2 and CR-4-k were written to create:

  and read it as a vitest module. The deployment rows are proved by shell drills
  at the repository root and by two static guards under `tests/static/`, none of
  which write `it(…)`, so all eighteen rows CR-2-j2 had just mapped read as "no
  such test file". The resolver now falls back to the repository root and reads a

### 4. `deploy/next/rehearsal/etl-drill.sh`

One command turns a legacy dump into a shop you can browse:

```sh
deploy/next/rehearsal/etl-drill.sh <dump.sql.gz> --uploads-root <dir>
deploy/next/rehearsal/etl-drill.sh --self-test        # synthetic fixture
```

MySQL 8, PostgreSQL 17 and Redis on a per-run network with loopback-published
ports; the dump imported decompressed inside the container from a read-only
bind mount; `db:migrate`, `db:seed`, `etl plan`, `etl run`,
`etl verify --full-digest`, `etl assets --execute`; then `web` and `edge` with
`VALIDATE_RESPONSES=1`, and one product, one published DIY page and one
attachment fetched over HTTP through the edge — the attachment compared by
sha256 against `attachments.sha256`, because nginx will serve a zero-length file
with a 200.

`--self-test` passes end to end. **It was run only against the synthetic
fixture**: a rehearsal against a copy of the production dump is data egress,
needs the user's go-ahead, and is not this stream's to run. No dump, hostname or
credential is in the repository.

Two things the self-test found on its first run, both of which would otherwise
have been found on cutover day:

- **`rsync -a` preserves the legacy tree's modes.** The old PHP-FPM pool's 0700
  directories make every product image a 404 in the new stack, with
  `stat() … (13: Permission denied)` in the edge log — which reads as "the
  uploads did not migrate" and is not that at all. The drill now `chmod -R a+rX`
  the destination, and `cutover.md` carries the same step.
- **`/readyz` is deep, and this drill runs no worker**, so it is 503 by design.
  Asserting a green `/readyz` would teach whoever runs this to ignore the line;
  the drill asserts database/redis/migrations are `ok` and names
  `worker: failed` as expected here and as a stop sign at a real cutover.

### 5. `deploy/next/cutover.md`

A runbook: prerequisites, the PLAN §6 window sequence, rollback, the retirement
PR list. Every command pasteable from the directory its section names, every
check with the output that counts as a pass. All 38 shell blocks pass `bash -n`.

Three things the old draft got wrong, all of which would have been found with
the clock running:

1. `deployment.env` was written to the top of the checkout. `lib/common.sh`
   resolves it from `deploy/next/`, so every script would have refused to start.
2. The hand-run Compose commands omitted `-p crmeb-next`. Compose names the
   project after the directory otherwise, which is a *different* project with
   different volumes — a second, empty stack beside the real one, and the switch
   would have routed the domain at it.
3. The ETL was "stream J's runner, see them", with no way to reach either
   database: neither the old MySQL nor the new PostgreSQL publishes a port. The
   runbook now opens two loopback `socat` bridges for the length of the window
   and closes them before the domain moves.

### 6. CR-1-j3 — resolved

Filed here (`docs/rewrite/cr/CR-1-j3.md`) because `handle.ts` picks its log
level from the status alone, so `/readyz`'s 503 — how a readiness probe says
"not yet", polled on every deploy — logged at `error` and buried the one line
that was not routine. P0-A landed the binder half in `56f2cdc0b`:
`defineRoute()` takes `expectedStatuses`, `handle()` logs those at `info`, and
the default does not move. This branch sets `expectedStatuses: [503]` on
`health.readiness` and adds
`health.int.test.ts::logs its 503 at info, not error (CR-1-j3)`, which drives
the real route against a real PostgreSQL and Redis with the heartbeat stopped
and asserts neither `warn` nor `error` was called. The CR is marked RESOLVED.

  on the pre-CR-1-j3 tree, then passed on the re-run, on three isolated runs and
  on the full suite again after the second merge (48 files, 1048 tests). It is a
  flake under parallel load, in D's area, and it is exactly what the
  `concurrency-soak` job added in §2 exists to catch. Not investigated further
  here.
- The `schedule` trigger has no `paths` filter, so the nightly run exercises the
  whole workflow, including `rehearsal` (45 min). That is a useful drift check
  on the default branch and a cost the orchestrator may want to trim.
