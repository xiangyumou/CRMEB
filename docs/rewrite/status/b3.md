## Ports changed

Both additions to `core/src/order/ports.ts` are the ones the brief grants, and
nothing else in that file moved.

```ts
interface FreightLine {
  …
  /** CR-1-f2. `freightTemplateId: null` cannot tell free from fixed. */
  freightMode: 'free' | 'fixed' | 'template';
  /** 分 per unit. `0` unless `freightMode === 'fixed'`. */
  fixedFreightFen: number;
}

interface PricingDraft {
  …
  /** CR-1-d2. Empty on the pricing pass, populated for `beforeCreate`. */
  adjustments?: readonly PriceAdjustment[];
}
```

`FreightLine` — the port used to re-read every SKU it had just been handed, once
per quote, only to discover whether `null` meant 包邮 or 固定运费. The mode now
rides on the line and `getSkusForSale` is gone from the freight path, along with
the local `LineMode` / `freightModesOf` helpers.

`PricingDraft.adjustments` — optional, because a contributor building a draft
for its own quote has no peers to report. `create` passes
`draft.discount.applied` into `beforeCreate`, so a kind handler can assert its
own adjustment landed without re-running its contributor inside the creating
transaction. Presale's `contributedAdjustment` and its `inTx` cast are deleted;
groupbuy gained `assertActivityDiscountApplied` (an equality — an adjustment
larger than the gap is as wrong as a smaller one).

Also fixed in `order.checkout.service.ts`, the same defect one layer up:
`gatherAdjustments` handed contributors and `coupon.quote` the plain `ctx`,
whose `db` is the pool, while `create` already held a pooled connection. Every
contributor and every coupon quote therefore took a **second** connection per
checkout — the deadlock CR-1-d2 §2 describes, in B1's own path. `readingThrough`
binds them to the caller's handle.

One seam was added outside `ports.ts`, in the catalog's own `index.ts`
(§6, below): `recordCartAdd(tx, ctx, { productId, skuId, userId, quantity })`.

### Divergence from the brief (CR-6-f1)

The brief says to move **all** of `trade`'s fields except `stockWarningThreshold`
onto `order`. Followed literally that creates duplicate settings, because by the
time this stream ran, every field in `trade` but one already had an owner that
reads it. Taking the CR's own argument — "two fields writing one timer is worse
than either name" — the duplicates are dropped instead:

| `trade` field                 | Where it lives now                                   |
| ----------------------------- | ---------------------------------------------------- |
| `autoReceiveDays`             | `order-fulfil.autoReceiveDays` (same legacy key)      |
| `autoReviewDays`              | `order-fulfil.reviewWindowDays` (same legacy key)     |

### Dead legacy keys found while folding

`catalog.autoReviewContent` and `refund.return*` claimed legacy keys that **do
not exist** in `crmeb/public/install/crmeb.sql` (`product_replay_content`,
`site_refund_name/phone/address`), while `trade` held the real ones. Deleting
`trade` without rehoming them would have silently dropped the operator's
configured values at cutover — and then failed the ETL run on an unmapped key,

## Routes, with fields (for H3)

Four new routes. Every field below is the wire shape; ids are strings.

### `GET /api/v1/orders/:id/gift-coupons` — `coupon.orderGiftCoupons`

`auth: 'user'`. `:id` is the surrogate id **or** the order number, like every
other storefront order route (CR-1-h). Errors: `ORDER_NOT_FOUND`.

Response `{ items: UserCoupon[] }`, each item:

| Field            | Type                                                         |
| ---------------- | ------------------------------------------------------------ |
| `id`             | string                                                       |
| `templateId`     | string                                                       |
| `title`          | string (snapshot at issue time)                              |
| `discountAmount` | money string                                                 |
| `minSpend`       | money string                                                 |
| `scope`          | `all_products` \| `category` \| `product`                    |
| `status`         | `unused` \| `used` \| `expired`                              |
| `sourceKind`     | always `gift_order` here                                     |
| `validFrom`      | instant                                                      |
| `validTo`        | instant                                                      |
| `usedAt`         | instant \| null                                              |
| `createdAt`      | instant                                                      |

An order that earned nothing answers `{ items: [] }` and `200`. A stranger gets
`404`, not `403` — `403` would confirm the order exists.

### `GET /api/v1/staff/coupons` — `coupon.staffList`

`auth: 'staff'`, no permission atom (the roster is `order-staff.staffUserIds`,
exactly like `order.staff.contract.ts`). A non-staff shopper gets `403` with
`details.reason = 'not staff'`.

Query: `page` (int ≥ 1, default 1), `pageSize` (int, default 20),
`keyword` (string, ≤ 50, optional, matches the coupon name case-insensitively).

Response `{ items: StaffCoupon[], total, page, pageSize }`, each item:

| Field               | Type                                             |
| ------------------- | ------------------------------------------------ |
| `id`                | string                                           |
| `name`              | string                                           |
| `discountAmount`    | money string                                     |
| `minSpend`          | money string                                     |
| `scope`             | `all_products` \| `category` \| `product`        |
| `validityMode`      | `fixed_window` \| `days_from_claim`              |
| `validFrom`         | instant \| null                                  |
| `validTo`           | instant \| null                                  |
| `validDays`         | int \| null                                      |
| `isUnlimitedSupply` | boolean                                          |
| `remainingCount`    | int \| null (`null` when unlimited)              |
| `perUserLimit`      | int \| null                                      |

`active` templates only: on a phone the one action is 发放, and a row that can
never be tapped is a support call. A sold-out template **is** listed, with
`remainingCount: 0`, so the staff member can see why it will not work.

### `POST /api/v1/staff/coupon-grants` — `coupon.staffGrant`

`auth: 'staff'`. Body `{ userId: string, couponId: string }` — singular, because
the phone's flow is 选客户 → 选券 → 发放.

Response `{ granted: number, skippedUserIds: string[] }`, the admin grant's own
shape. A customer who already holds the coupon up to its `perUserLimit` comes
back as `{ granted: 0, skippedUserIds: ['<userId>'] }` and a `200`, not a `409`
— nothing went wrong.

Errors: `COUPON_TEMPLATE_NOT_FOUND`, `COUPON_GRANT_USER_UNKNOWN`,
`COUPON_SOLD_OUT` (a sold-out campaign **is** a refusal: pick another coupon).

It delegates to `adminGrant` unchanged, so the supply decrement, `issueOne`'s
insert-before-decrement ordering (COUPON-008) and the per-user limit are one
implementation and the phone cannot oversell what the web console protects.

### `GET /api/v1/groupbuy/summary` — `groupbuy.summary`

`auth: 'public'` — a signed-out visitor is exactly who the social proof is for.
No params, no query. Response:

| Field          | Type                                                        |
| -------------- | ----------------------------------------------------------- |
| `participants` | int ≥ 0 — distinct users in a live team                     |
| `avatars`      | string[], ≤ 8, most recent participant first, may be empty  |

Legacy's `getCombinationIndex` counted rows in `store_pink`, refunds, failed
teams and repeat joins included, so the number only went up and routinely
exceeded the shop's customer count. Here "live" is one predicate shared by the
count and the avatars: a `joined` member, in a `forming` or `succeeded` group,
on an activity that is `active`, not deleted, and inside its window.
`count(distinct user_id)`, so one shopper in two teams is one person; the
avatars are a `distinct on (user_id)` newest-first, so nobody appears twice.

Cached 60 s in Redis under `groupbuy:summary`. Both the get and the set are
best-effort: a Redis outage logs at `warn` and falls through to the database
rather than failing the tab.

## Decisions

1. **The 订单赠券 route lives in `order`, not `coupon`.** The hard half is
   ownership, not the coupon read. `requireOrderRef` only *resolves* `:id` (an
   order number is looked up for this user; a bare surrogate id is taken at face
   value, because every previous caller went on to read the order). Without an
   explicit `findOrderForUser` a stranger got `{ items: [] }` and a `200`, which
   still tells them the id is not theirs. `order.giftCoupons` loads the order for
   the caller, `404`s, and only then asks `coupon.listOrderGifts`.

2. **Gift coupons were already granted; this unit is the read.** `onOrderPaid`
   records an `order.auto-deliver` effect, `autoDeliver` calls
   `coupon.grantOrderGifts`, idempotent through `user_coupons_order_gift_uq`.
   Legacy's `give_coupon_ids` path has been covered since B1.

3. **满额包邮 belongs to the freight port, not to checkout.** It was already
   implemented in `computeFreight` step 5, guarded by `freeThresholdFen > 0`;
   what CR-1-f2 needed was the *mode* on the line, because checkout cannot zero
   a fixed-postage line it has already been quoted for. The port is the only
   place that sees the whole order. Four int tests pin it from four angles;
   the first is named by invariant FREIGHT-003 and its name is now commented as
   load-bearing (it was renamed during this stream and had to be put back).

4. **`product_events { kind: 'cart' }` goes through a catalog seam.** The cart
   may not reach `catalog.repo` (CONVENTIONS: a repo is private to its domain)
   and its own repo has no business writing a catalog table, so
   `catalog.recordCartAdd(tx, ctx, …)` is the whole seam — no read, no verdict,
   one insert — shaped `(tx, ctx, input)` like `checkPurchaseAllowance`. The
   cart calls it inside the `ctx.withTx` it already had, beside the
   `cart_items` upsert, so the number and the row commit together. The event
   carries the **delta**, so 加购件数 sums units and not taps, and it is never
   retracted: emptying the cart does not un-add it, because the metric is
   interest, not inventory. `stats.repo.ts`'s "nobody writes this yet" comment
   was corrected; `user_visits` (CR-1-f3 §1) still has no writer and is not this
   stream's.

5. **The staff console reuses `adminGrant` verbatim.** More important than the
   saved code: COUPON-008's ordering and the per-user limit are one
   implementation across both surfaces.

## Fixed in passing

**`@shop/testing`'s mock server had a non-total comparator.** `bySpecificity`
returned `0` for two unrelated paths, so `Array.prototype.sort` produced
whatever the pairs it happened to compare allowed. Adding a contract *anywhere*
in the tree moved `/api/v1/addresses/:id` ahead of `/api/v1/addresses/default`
and the literal route started answering `422` — a failure in a file nobody had
touched. The comparator now orders whole shape keys and then the path itself,
and `mock-server.test.ts` pins the rule from both input orderings.
