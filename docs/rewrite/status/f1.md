### What other streams need from these contracts

1. **Config groups are listed, not hard-coded.**
   `GET /admin-api/system/config-groups` returns every group that
   `defineConfigGroup` registered; `GET`/`PUT /admin-api/system/config/:group`
   read and write one. To add a settings page, a domain writes
   `packages/core/src/<domain>/<group>.config.ts` and imports it from its
   `index.ts` — no route, no page, no menu entry of its own.
2. **Secrets never travel.** A field with `secret: true` comes back in `values`
   as a **boolean** "is set" flag. A save that omits the key leaves the stored
   value untouched. No route returns a stored credential, ever.
3. **Upload routes declare no `body` schema**, because the request is
   `multipart/form-data` and `handle()` only parses JSON. Everything a caller may
   choose (`categoryId`, `directory`, `purpose`) is a query parameter. The
   storage key is server-generated and is never an input.
4. **The category tree arrives flat** (`parentId` + `depth` + `path`, depth-first
   order) and the client nests it. A self-referential zod schema is legal but
   overflows the stack in `zod-to-openapi`, and `CrudTable` wants a flat list.
5. `POST /api/v1/uploads?purpose=avatar|review|refund` is the storefront upload
   (E1 avatars, A reviews, C refund evidence). It needs a user session, is rate
   limited per user, takes images only and answers with a renderable URL.

## How to use what this stream ships

### Declaring a config group

Write `packages/core/src/<domain>/<group>.config.ts`:

```ts
import { z } from 'zod';
import { defineConfigGroup } from '../kernel/config-registry';

export const shippingConfig = defineConfigGroup({
  group: 'shipping',           // globally unique; a duplicate THROWS at import
  title: '配送设置',
  permission: 'system:config:read',   // omit and any admin who can open 系统设置 may read it
  schema: z.object({
    freeOver: z.number().int().min(0).default(0),   // every field needs .default()
    apiKey: z.string().max(128).default(''),
  }),
  ui: {
    freeOver: { label: '满额包邮（元）', type: 'number', section: '运费' },
    apiKey: { label: '接口密钥', type: 'password', secret: true },
  },
  legacyKeys: { freeOver: 'store_free_postage' },   // old eb_system_config.menu_name
});
```

then **import it from the domain's `index.ts`** and add one line to
`core/src/system/config-groups.ts` until CR-3-f1's generated bucket lands.
That is the whole job: the settings index lists it, `/admin/system/settings/:group`
renders it, the ETL routes the legacy keys into it, and
`ctx.config.get(shippingConfig)` reads it typed.

Three rules the registry enforces, with the reason:

- **every field has `.default()`** — a fresh install must boot before anybody
  has opened the form;
- **`secret: true` on every credential** — the read returns `true`/`false`, not
  the value, and a save that omits the key keeps what is stored. There is a test
  that walks every registered group and fails if a field whose name looks like a
  credential is not marked (`system.test.ts::describeGroup > marks every
  credential in every registered group as secret`);
- **group names are global.** Check with
  `grep -rn "group: '" packages/core/src --include='*.config.ts'` before picking
  one. B1 and F1 both picked `order`; see CR-6-f1.

### Using `AssetSource` (the kit's `AssetPicker`)

Already installed. `app/admin/(shell)/layout.tsx` wraps the shell in
`<StorageAssetSourceProvider>`, so any admin page can use the kit's
`<AssetPicker>` / the `asset` config field kind and it browses the real media
library, uploads into it and deletes from it. No per-page wiring, no props.

If a page needs the source directly:
`createStorageAssetSource()` from `@/admin/storage/asset-source`.

### Uploading a file from an admin page

`callRoute` sends JSON only, so use the adapter (CR-4-f1 asks for it in the kit):

```ts
import { uploadFile } from '@/admin/storage/upload';
import { storageAttachmentUpload } from '@/admin/api/contracts';

const row = await uploadFile(storageAttachmentUpload, { query: { categoryId } }, file);
```

It reuses the kit's base URL, cookies, `ApiError` mapping and 401 handling.

## Decisions

- **Agreements are a config group, not a table.** The three legal texts live in
  the `agreement` config group, so the admin edits them through the same generic
  settings screen as everything else and there is no fourth CRUD screen to
  maintain. `GET /api/v1/agreements/:key` is the storefront's public read.
- **Profile routes declare `auth:session:read` / `auth:session:delete`**, the two
  atoms every authenticated admin holds implicitly, because an admin with no
  grants at all must still be able to read their own profile and change their own
  password. CR-2-f1 asks for dedicated profile atoms.
- **SVG is refused unconditionally**, script or not. A sanitiser is a moving
  target and the media library is served from our own origin; a shop that needs a
  vector logo can upload a PNG. Same reasoning refuses HTML, PHP, executables and
  bare archives, by magic bytes rather than by extension
  (`core/src/storage/file-type.ts`).
- **The declared MIME must agree with the bytes.** A mismatch is refused, not
  corrected: "this PNG is really a PDF" is either an attack or a bug, and
  silently relabelling it makes both invisible.
- **Storage keys are server-generated** (`yyyy/mm/<sha256-prefix>.<ext>`), never
  an input. The legacy `videoDataSave` took a client path; that is the whole
  reason the old uploader could write anywhere.
- **Scan-upload tokens are per-admin, single-use, short-lived**, stored in Redis
  and burned inside the same conditional as the upload. The legacy
  `scan_upload` token was a single global constant. A refused file does **not**
  burn the token — the operator retries with a valid photo.
- **The remote import resolves the hostname itself, judges every returned
  address, and then connects to the address it judged**, presenting the original
  `Host`. Judging the name and then letting `fetch` resolve it again is the
  classic DNS-rebinding hole. Redirects are re-judged the same way.
- **A folder delete and filing into that folder serialise on the category row.**
  The emptiness guard is a `NOT EXISTS` over `attachments` inside the UPDATE,
  which serialises two deletes but not a delete against an upload: they write
  different tables, and under READ COMMITTED neither sees the other's
  uncommitted row. Both committed and the picture ended up in a deleted folder,
  invisible everywhere. Now the delete takes `SELECT … FOR UPDATE` on the
  category row and *then* runs the guarded update as a separate statement (fresh
  snapshot), while every path that files into a category — upload, import, batch
  move, child-folder create, re-parent — takes `SELECT … FOR SHARE` on that row
  inside the same transaction as its insert. `FOR SHARE`, not `FOR KEY SHARE`:
  `deleted_at` is a non-key column and `FOR KEY SHARE` does not conflict with
  updating it. The kernel's `lockRow` is `FOR UPDATE` only, so the share-mode
  lock is a small repo helper, `storage.repo.ts::lockCategoryAlive`.
- **Saving config has no side effects.** The legacy settings save wrote SSL
  certificate files to disk. Here a save writes rows; anything that needs to
  happen because a value changed is a job, not a write from inside the form
  handler.
- **`sha256` is the dedupe key and is never invented.** The ETL leaves it null
  and reports `needsDigest`, so the migration runner computes the real digests
  over the copied objects. A placeholder would silently disable dedupe forever.
- **Legacy role grants are not translated.** The old `rules` column holds
  `eb_system_menus` ids — rows in a table that no longer exists. Guessing which
  atoms they meant is guessing who may issue refunds, so every affected role is
  listed in the migration report (`roleIdsNeedingRegrant`) for re-granting by
  hand.
- **MD5 passwords stay MD5.** The column carries the algorithm, so login
  verifies the old hash once and upgrades it to bcrypt on the way through.
  Re-hashing at migration time needs the plaintext, which nobody has.
- **`order_cancel_time` is converted from hours to minutes** by the ETL. It is
  the one unit change in this stream and the one that silently ruins a shop if
  missed: copying `2` across would cancel every unpaid order after two minutes.
- **The `order` config group went to B1** when the merge revealed the collision;
  F1's remaining fields became the `trade` group. CR-6-f1 asks which of the two
  screens the operator should see.
- **The audit log records writes only.** A read that is worth recording is a
  different feature (access logging) with a different retention policy; mixing
  them makes the write history unreadable, which is what it is for.

## Deferred / not done

- **`sharp` is not used.** Image dimensions are read from the file header
  (`probeImageDimensions`: PNG IHDR, GIF screen descriptor, JPEG SOF) rather than
  by decoding the image. It reads the four formats the shop accepts, costs no
  dependency and no native build approval, and cannot be made to allocate a
  gigabyte by a crafted header. **No thumbnails are generated** as a result: the
  attachment list renders the original with browser-side sizing, and
  `thumbnailUrl` is carried through the schema for migrated rows that have one.
  If a shop needs real thumbnails, that is a `sharp` job in the worker, not a
  change to the upload path.
- **The S3 driver signs its own requests** (SigV4, ~120 lines, tested against
  AWS's published example vectors) instead of pulling in `@aws-sdk/client-s3`.
  Upload, delete and public-URL construction are all it needs.
- **Dashboard numbers are F1's own** (admins, media library, pending items via
  the `DashboardContributor` registry). F2's tiles register themselves later; a
  contributor that throws degrades to one missing tile, not a broken page.
- **No agreement version history.** The legacy system kept none either, and the
  audit log records who changed the text and when.

## New dependencies

**None.** Nothing was added to any `package.json`, so `pnpm-lock.yaml` is
untouched and no pnpm build-script approval is needed.

Three things that would ordinarily be dependencies are implemented instead:
SigV4 signing (`core/src/storage/s3.ts`), magic-byte sniffing and the image
dimension probe (`core/src/storage/file-type.ts`), and multipart parsing
(`core/src/storage/multipart.ts`, over the platform `Request.formData()`). The
QR code for scan-upload is antd 6's own `<QRCode>`.
