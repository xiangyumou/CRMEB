## Decisions

- **The webhook route does not use `handle()`.** `handle` parses, authenticates,
  answers JSON errors and sets a JSON content type; WeChat sends form-encoded
  query parameters with an XML body, reads anything but the literal `success`
  as a failure, and retries three times before telling the customer
  该公众号暂时无法提供服务. The route builds its own `Ctx` from the container
  and returns `text/plain` or `text/xml`. `auth: 'webhook'` in the contract is
  what documents it.
- **No `registerWechatOaDomain()`.** The domain registers no effect handler and
  no order hook, so the side-effect import in `domains.gen.ts` is the whole
  registration. (This also side-stepped the hyphenated-domain assertion that
  CR-1-e3 described; integration fixed that from the other side in `cdc04601`.)
- **Media is picked, never typed.** Every reply that carries a `media_id` is a
  select over `wechat_media`, not a text box. A hand-typed handle fails as
  `40007` in a customer's chat, minutes after the form said 已保存 and with
  nothing on the admin screen to say so.
- **Saving a menu is not publishing it, in the UI as in the routes.** 发布 is a
  confirm dialog behind `wechat-oa:menu:publish`, and the last `publishError`
  is an alert on the page rather than a toast that has already gone.
- **The fake WeChat server lives in the domain** (`wechat-oa.fake-oa.ts`).
  `@shop/testing`'s fake gateway is WeChat _Pay_ v3 — different host, different
  auth, different body — and nothing may reach the real API. CR-2-e3 proposes
  moving it into `@shop/testing/wechat`, which is orchestrator ground.
- **The app credentials live in the `wechat` group alone** (CR-1-j, decided by
  the orchestrator). `wechat_appid` / `wechat_appsecret` were mapped by both
  that group and F1's `wechat-oa`, so a migrated shop held the app id in one
  screen and a blank in the other. F1's group dropped the two fields and their
  `legacyKeys`; `oaCredentials` now reads C's. The token and the AES key are
  still declared in both, so they keep the F1-first fallback — CR-3-e2 covers
  that half.
- **The JS-SDK host check asks the deployment, not a config group.** It calls
  `publicOrigin(ctx)` / `isTrustedHost(ctx, host)` with stream N1's signatures,
  standing in locally in `wechat-oa.trusted-hosts.ts` until N1 lands them in
  `@shop/core/system`; `notification.siteBaseUrl` is no longer read.

## Defects found and fixed in the inherited code

1. **`parseXml` returned `{}` for every real callback.** The bare-value branch
   was `[\s\S]*?`, which matched the whole `<xml>…</xml>` document as one
   element named `xml` — which the parser skips. Every message therefore had no
   `FromUserName`, the webhook answered `success` to everything, and no reply,
   follow or scan was ever recorded. Now `[^<]*`.
2. **`wechat_qrcode_scans.created_at` came from the database default** while the
   counter beside it came from `ctx.clock`, so the daily channel report and the
   totals disagreed — visibly under a fake clock, invisibly across timezones.
3. **Publishing two menus at once left one publish rejected by the index.** See
   the race list below.
4. **Four unique violations surfaced as 500s** (keyword, subscribe singleton,
   scene, category name) — each is now the 409 the pre-check would have given.
5. **A cold jsapi ticket cache made one WeChat call per request.**

## Files touched outside E3's paths

All of these were required by the CR-1-j decision — deleting two fields from a
config group breaks every reader of them, and the readers live in three other
streams. Flagged by owner:

**F1 (system config):**

- `packages/core/src/system/wechat-oa.config.ts` — dropped `appId` /
  `appSecret`, their UI entries and their `legacyKeys`; the 启用公众号 switch
  now says where the AppID moved to.
- `packages/core/src/system/system.int.test.ts` and `system.test.ts` — the
  secret-masking tests exercised the rules through that group's `appSecret`.
  They now use `encodingAesKey` (the secret the group still has) and
  `verificationFile` beside it. Same assertions, same intent.

**E1 (storefront auth):**

- `packages/core/src/user/storefront-auth.service.ts` — `oaAuthorizeUrl` and
  `oaLogin` read `wechatOaConfig.appId`, which CR-1-j deleted. Both now go
  through one `oaApp(ctx)` helper that reads the app id from the `wechat`
  group and treats "OA configured" as `oa.enabled && appId !== ''`, so a shop
  that flipped the switch but never filled the credentials still gets
  `AUTH_WECHAT_NOT_CONFIGURED` instead of a WeChat error page.
- `packages/core/src/user/storefront-auth.int.test.ts` — the OA `beforeEach`
  seeds `wechatConfig { oaAppId }` alongside `wechatOaConfig { enabled }`.

**J (ETL):**

- `packages/etl/src/config.test.ts` — the test proving the legacy-key index
  fans out used `wechat_appid` as its live example, and CR-1-j is exactly what
  collapsed that key to a single claimant. It is now two tests: one guarding
  the decision (`wechat_appid` → the `wechat` group alone) and one keeping the
  fan-out coverage, on `routine_appId`, which is still claimed twice (see the
  note below).

## Notes for the orchestrator

- `WECHAT_OA_CATEGORY_NAME_TAKEN` is a new error code in
  `packages/contracts/src/wechat-oa/errors.ts`, wired into the two category
  routes' `errors` lists.
- The ETL mapper will cover menu, auto-replies and QR codes only.
  `eb_wechat_user` is E1's (`packages/etl/src/mappers/user.ts` maps it into
  `wechat_identities`) and is deliberately not touched here.
- The ETL mapper keeps a migrated channel code's **legacy numeric id as its
  scene string** (`sceneOf(legacyId) === String(legacyId)`). Posters already
  printed carry that number, and WeChat echoes it back on every scan; minting
  new scene strings at migration would orphan every poster on a wall.
- **CR-1-j has an unsettled sibling.** The same two-claimants problem it fixed
  for the Official Account still stands for the mini program:
  `packages/core/src/system/wechat-mini.config.ts` maps `appId: 'routine_appId'`
  and `packages/core/src/wechat/wechat.config.ts` maps
  `miniAppId: 'routine_appId'`. A migrated shop will see the mini-program app
  id in one screen and a blank in the other, which is the symptom CR-1-j was
  filed about. E3 did not touch it: neither file is E3's, nothing in
  `wechat-oa` reads either field, and the fix is the same one-line decision the
  orchestrator already made once. `packages/etl/src/config.test.ts` now pins
  the duplication, so whoever resolves it will be told by a red test.
- `docs/rewrite/invariants.md` was conflicted in the main checkout when this
  stream last looked, so the invariant→test mapping above lives here rather
  than being written into that file. It is a copy-paste when the orchestrator
