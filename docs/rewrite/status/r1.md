## CR-50-k2 — RESOLVED (`2f57b9a3a`)

The resend guard is now the write itself. `sendVerificationCode` begins with
`claimResend`, which runs `SET sms:resend:… <token> NX PX <resendMs>`. A caller
that loses gets `AUTH_SMS_TOO_FREQUENT` with `retryAfterMs` from the key's
`PTTL`. A budget refusal, a provider refusal or any other throw after the claim
gives the window back through `releaseResend`, a Lua compare-and-delete on the
token, so it can never delete a later caller's claim. `issueCode` no longer
writes the resend key.

- **flipped** `sms/sms.resend-race.int.test.ts::…` (`it.fails` → `it`). Its
  barrier now holds each caller's first touch of the key (`PTTL` or `SET`),
  because the fixed code no longer reads before it writes. With the old service
  put back it fails (5 sent).
- **added**, same file: a budget refusal leaves no resend key; a provider
  refusal leaves no resend key; a release never deletes a later caller's claim.

## CR-41-k2 — RESOLVED, items 1 and 3, option 1

- **Request path.** `productDetail` inserts one `product_events` view row on
  the pool: no transaction and no `UPDATE products`. `bumpProductViews` has
  been deleted. The `views` the shopper sees is the folded count, up to about
  a minute behind.
- **Fold.** `catalog/catalog.views.ts::foldProductViews` runs one
  `UPDATE products … FROM (SELECT product_id, count(*) … GROUP BY product_id)`
  per batch of event ids (`repo.foldViewEvents`). The batch is 50 000 ids, and
  a run does at most 20 batches.
  - It stops at `repo.lastSettledEventId(graceMs = 10 s)`, measured on the
    database clock that `created_at` defaults from. An id that has been handed
    out but not yet committed is therefore never stepped over.
  - A Redis watermark, `catalog:views:folded-through`, is claimed with a
    compare-and-set before each write and handed back if the write fails.
    Overlapping runs never fold a range twice, and a crash between claim and
    write loses at most one batch. This is a display counter; the events
    themselves, which the reports read, are untouched.
  - If the watermark is missing, or ahead of every event (a restore or a
    truncate), the run sets it to the newest settled event and folds nothing.
- **Worker.** `apps/worker/src/jobs/catalog.foldProductViews.ts` runs every
  60 s with concurrency 1.
- **Item 2** (a Redis `INCR` live counter) is not done. The shopper never saw a
  live count.

Tests added:

- `catalog/catalog.int.test.ts::product views, folded by the worker (CR-41-k2)` (6): the request path leaves the product row alone; the fold is once and only once, skips non-view events, works in batches with a bounded run, respects the grace period, handles two overlapping runs (6 views, 6 counted), and resets a watermark that is ahead of every event.
- `catalog/catalog.concurrency.int.test.ts::a promotion sending everyone to one product page`: 8 parallel detail reads while another transaction holds the product row through an `UPDATE`. All 8 are served and all 8 rows land. With the old service and repo it fails with `queued on the row lock`.
  - The CR suggested `SELECT … FOR UPDATE` as the holder, but that still blocks the insert, because the event's foreign key takes `FOR KEY SHARE`. Only a key change or a delete takes `FOR UPDATE`, and neither is a hot path.

**Deploy note.** The first fold after deploy only sets the watermark. Views
recorded between the deploy and that first run, at most about a minute's
worth, are not added to `products.views`.
