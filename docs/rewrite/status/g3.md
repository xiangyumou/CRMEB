## Item 2 — CR-2-g2, 超级组件 leaves the palette (done)

Option 3, as decided. `CREATABLE_COMPONENT_KEYS` in
`packages/contracts/src/diy/schema/registry.ts` now also excludes
`customComponent`, so the palette offers **27** keys instead of 28.

What deliberately did **not** change:

- `customComponent` stays in `DIY_COMPONENT_KEYS` and in
  `RENDERABLE_COMPONENT_KEYS`, so the canvas and the uni renderer still draw it;
- `customComponent.panel.tsx` stays registered, so an existing 超级组件 node is
  as editable as before;
- `customComponents` is still never read or written by the panel, so the inner
  layout round-trips byte for byte;
- it is **not** added to `RENDER_ONLY_COMPONENT_KEYS` — that set means "no panel
  in the old admin either", which is not true here.

Pinned by a new registry test and recorded as **DIY-009** in
`docs/rewrite/invariants.md`. Counts updated in `status/g1.md` and
`status/g2.md`.

> This is the one edit outside the paths the brief calls G3's own; the brief
> asks for it in as many words ("Remove `customComponent` from
> `CREATABLE_COMPONENT_KEYS`"), and it is a one-line filter plus its test.

## Item 3 — CR-3-g2, the factory defaults (done)

Eight `defaults/*.default.ts` extended with exactly the groups their legacy
`patchConfig` / `defaultConfig` merge injects. The shapes were **read off the
`.vue`**, not guessed: a Node replay harness evaluated each `patchConfig` body
(with `this.$set(o,k,v)` rewritten to `o[k]=v`) against the current default
object and emitted only the keys it newly created, so `min` / `max` / `tabList`
/ `default` and the key order match the legacy file.

| Component                                               | Keys added |
| ------------------------------------------------------- | ---------- |
| `member`                                                | 46         |
| `customComponent`                                       | 7          |
| `productInfo`                                           | 2          |
| `articleList`, `videos`, `pictureCube`, `promotionList` | 2 each     |
| `menus`                                                 | 1          |

Zero existing keys were mutated. The four-sided `paddingConfig` /
`marginConfig` pairs are kept in step with the older scalar sliders
(`topConfig` / `prConfig` / `bottomConfig` / `mbConfig`) the way
`userInfor.default.ts` does, because the uni renderer still falls back to the
scalars; a test asserts the two agree.

Three keys are deliberately **not** added, and the tests say so rather than
leaving the absence to be re-measured later:

- **`c_common_style`** (`{color, color2, lr, type}`) — injected by `c_video`,
  `c_picture_cube` and `c_home_coupon`. No uni renderer reads it; this CR calls
  it debris and it is.
- **`timestamp`** — in `c_product_info.vue`'s `defaultConfig`, but the editor
  store owns it (G1's rule: `timestamp`, `name`, `cname` belong to the store).
- **`customComponents`** — `c_custom_component.vue`'s `patchConfig` never
  creates it; only the inner designer's save at `:633` does, and that designer
  is out of scope (CR-2-g2).

Rules that still hold, all covered by the suite: no panel writes on open; "open
every panel, change nothing, save" is deep-equal on all three production
fixtures; each touched default validates against its component schema; and a
new `CR-3-g2` describe block asserts, per component, that the default now
carries every group its legacy panel can inject.

### 3a — `DiyPickerKind`: `labels` yes, `brand` no

`labels` is wired to `catalog.adminLabelList` (merged), so
`_fields/pickers.tsx`'s `DiyGoodsLabelField` stops being remove-only and becomes
an ordinary picker. `list` and `activeValue` are kept in step exactly as
`closeStoreLabel` does — write `list`, recompute `activeValue` from it — the row
keeps the legacy `label_name` key rather than the DTO's `name` (the renderer
reads `label_name`), and a numeric id goes back as a number so a node written
here matches one written by the old admin.

**`brand` is dropped.** `eb_store_brand` is not in the frozen schema: no table,
no route, nothing to page. The two legacy rows that used `c_brand`, both named
in `data-source.tsx`:

- `c_home_goods_list.vue:77-81` — 商品列表's `brandList`, in the 筛选商品 branch.
  The key is in neither `goodList.default.ts` nor `goodList.schema.ts`, so the
  row was **already unreachable** before this stream; an older node carrying one
  keeps it untouched.
- `c_promotion.vue:75` — 商品选项卡's per-tab `brandConfig.brandVal`.
  `_fields/promotion-tabs.tsx` shows it **read-only** rather than dropping it,
  and still draws the 品牌 source branch when a tab says that is its source.

If 品牌 is ever added to the schema, this is one `DiyPickerKind` member, one
case in `catalog-source.ts` and swapping two fields. No panel changes.

### 3b — 图片魔方 样式十一: the CR is off by one, nothing to build

CR-3-g2 read `c_pictrue.vue:178` (`v-if="style === 11"`) as 样式十一's editor.
`style` is `styleConfig.tabVal`, which is a **0-based** index into
`c_button_style.vue:132-199`. That list has eleven live entries, `cube2` …
`cube12`, so its last index is **10** — 样式十一 is the one-cell `cube12` layout
and `_fields/cube.tsx` already edits it like any other.

Index 11 is `cube1`, the 16-cell free-draw grid at
`c_button_style.vue:199-204`, and it is **commented out**. The shipped legacy
admin cannot select it either, exactly like `zIndexConfig` (CR-1-g2 note 2). So
there is no reachable canvas to port and no selectable style to hide — the
brief's "leave it selectable for existing nodes only" is already the state of
the world.

What had to be guaranteed instead is that a page saved while that entry _was_
live is not damaged. `_fields/cube.tsx` never reads or writes
`picStyle.docPicList`, and a new panel test opens such a node (tabVal 11,
sixteen cells, sixteen areas), asserts no write, edits a cell's link and asserts
the areas survive. The storefront still draws them
(`pictureCube.vue:330-331`).

**Decision: not built.** Under a day's work or not, there is nothing an operator
can reach. Recorded in the `cube.tsx` doc comment and as a correction on
CR-3-g2.

## Item 4 — real pickers over the catalog contracts (done)

`admin/diy/catalog-source.ts` is the real `DiyDataSource`, plus the `targets`
callback `<LinkPicker>` wants. `editor.tsx` installs both.

| Kind / tab           | Route                       | Notes                                                                                                                           |
| -------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 商品                 | `catalog.adminProductList`  | `tab: 'on_shelf'` — a DIY page must not advertise a product the shopper cannot open, which is how the legacy picker filters too |
| 商品分类             | `catalog.adminCategoryTree` | flattened into `DiyTreeNode`, nesting kept; the link tab shows the full trail and searches it                                   |
| 商品标签             | `catalog.adminLabelList`    | `isEnabled: 'true'`                                                                                                             |
| 文章 / 优惠券 / 拼团 | —                           | delegate to `createStubDiyDataSource()` until streams F2 and D ship their lists                                                 |

`resolve('product', ids)` is one `catalog.adminProductDetail` per id, each in a
try/catch so a deleted product shows as `#id` instead of blanking the picker. It
only runs for legacy payloads that stored bare ids — the pickers store the row
whole (id, name, image), because the renderer paints from the payload before any
API answers and dropping those fields would change what the storefront shows.

A plain object built on `callRoute` rather than hooks: `DiyDataSource` is a port
a picker calls **inside** its own `useQuery`, so the caching, dedupe and
cancellation are already the picker's. Nine tests in `catalog-source.test.ts`
drive it through a stubbed `fetch`, so the query string the admin API actually
builds is part of the assertion.

Replacing a delegated kind later is one case in `list` and one in `resolve`.
**No panel changes**, which is the whole point of the port.

## Decisions, in one place

1. `customComponent` leaves the palette but stays renderable and editable
   (CR-2-g2 option 3, as briefed).
2. `c_common_style`, `timestamp` and `customComponents` stay out of the
   factory defaults, for the three different reasons above.
3. `brand` is not a `DiyPickerKind`; `eb_store_brand` is not in the schema.
4. `member`'s `leftMenuConfig` is in the default (the legacy `patchConfig`
   injects it) but `member.panel.tsx` draws **no row** for it — the legacy panel
   only renders it under 样式二, which this port does not offer. The key is
   carried, not edited. One existing panel assertion was retargeted from
   `leftMenuConfig` to `memberConfig` to say this out loud.
5. 图片魔方's free-draw canvas is not built, because it is unreachable in the
   old admin too (item 3b).
6. CR-1-g2's three trailing notes are **not** applied; its own annotation now
   says so.
