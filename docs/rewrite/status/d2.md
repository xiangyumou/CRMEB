## Decisions

1. **Full payment only; the deposit columns stay inert.** `assertFullPayment`
   refuses `paymentMode: 'deposit'` at `beforeCreate` and the admin form cannot
   create one (422). Legacy never read the columns on the order side either
   (`deposit` appears in exactly one PHP file, the admin save parameter list).
   The ETL keeps a legacy 定金 campaign's numbers but imports it `paused` — a
   campaign nothing can sell does not belong on the shelf.

2. **One line per presale order.** `presale_stock_ledger_order_reason_uq` is
   `UNIQUE (order_id, reason)`, so an order can record one reservation and one
   release; a two-line order could not say what it took. Legacy agreed in
   practice — a presale was bought through 立即购买, never from a mixed cart.

3. **Presale stock is its own counter, and four ledgers move together.** The
   campaign's `stock`/`sales`, its SKU's, and the product's two, all inside the
   order transaction. Every movement is written to `presale_stock_ledger` with
   all four deltas, so a restore is one row read rather than four
   recomputations (REFUND-002, QUEUE-008).

4. **The sale has no ledger row of its own.** `presale_stock_ledger_reason` has
   two values and the schema is frozen, so payment *amends* the reservation row
   (`markLedgerCommitted`) instead of writing a third. Without it a refund's
   `-quantity` on `sales` balanced against nothing and the ledger read as a
   deficit — caught by `isBalanced` in the refund test.

5. **The quota is enforced where `sales` moves, not at reservation**
   (STOCK-004, revised). `total_quota` is a lifetime ceiling on units *sold*
   and `sales` only moves on payment, so a check at checkout compares against a
   number that has not moved: with `stock: 100, total_quota: 1`, a hundred
   shoppers each read `sales = 0` and each pay. `commitActivitySales` now
   carries the quota in both `WHERE`s and returns `false`; the reservation-time
   check stays as the cheap early refusal.

6. **A payment the quota refuses is refunded, not rolled back.** The money has
   arrived. The campaign's units go back, the stage becomes `cancelled`, and a
   `presale.refund` effect is recorded; its handler opens its own transaction
   and calls `refund.refundSystemInitiated(tx, ctx, { orderId, reason:
   'presale_expired', note })`. `AutoRefundPort` survives only as the seam a
   test substitutes a spy into — the default *is* the refund domain, so every
   `refunds` row still goes through C's entry point and ceiling check. A throw
   is still the right failure: the dispatcher parks the row in C's 待处理任务
   console for a human.

7. **`final_due_at` stays null for a full-payment presale.** The deadline for
   that payment is the order's own expiry and B1 owns it; a second countdown
   would be a second answer to the same question.

8. **发货承诺 is frozen at payment, not recomputed.** An operator who shortens
   `shipAfterDays` later does not move a promise already made
   (`presale_orders.ship_not_before_at`).

9. **`ended` is terminal and is what the sweep writes.** The admin offers
   启用/暂停 in one click and does not offer 结束: an operator who wants a
   campaign gone sooner moves the end time or deletes it.

10. **The CR-1-d guard compares the contributor's output, not the goods
    total.** A `PricingContributor` does not rewrite line prices, so comparing
    the campaign total against `draft.goodsTotal` refuses every correctly
    priced order. `beforeCreate` asks the contributor registered under
    `presale:activity-price` what it takes off *this* draft — run against the
    open transaction, because a second pooled connection inside the order
    transaction deadlocks at pool width. See CR-1-d2 and CR-2-d2.
