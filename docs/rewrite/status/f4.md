### `GET /api/v1/site/config` — `auth: 'public'` (CR-7-h2 §1)

of its source groups is written. `ETag: W/"<version>"` + `Cache-Control:

### `POST /api/v1/attachments/base64` — `auth: 'user'` (CR-7-h2 §2)

Body `{ url: string }` → `{ dataUrl: string }`. Refusals are all one code,
`ATTACHMENT_URL_NOT_ALLOWED` (422), deliberately: an endpoint that told "host
not allowed" apart from "connection refused" would be a network scanner with a
shop attached. The reason goes to the server log.

Accepted URL forms — **this shop's own attachment and nothing else**:

- a `/`-path, resolved against `publicOrigin(ctx)` (refused outright when the
  origin is `''`);
- an absolute `http(s)` URL whose host `isTrustedHost` recognises
  (`site.publicOrigin` + `site.extraOrigins`);
- a URL under the storage driver's `s3PublicBaseUrl`, prefix-matched on the
  path.

Refused: another host, `//host` (protocol-relative), embedded credentials, a
non-`http(s)` scheme, a name that resolves to a private / loopback / link-local
/ metadata address (DNS resolved first, every address judged, connection made
by IP with the original `Host`, every redirect re-judged — F1's `safeFetch`),
a body over **2 MB**, and anything that is not `image/{png,jpeg,gif,webp,bmp}`
by signature. SVG is never an image. Rate limited to **60/hour per user**.

**Both uni-app callers map to this one route**: `api/public.js` `imageBase64`
and `api/user.js` `imgToBase`. They are the same call under two names.

### `GET /api/v1/diy/pages/user-center` — `auth: 'public'` (CR-3-h2 §1)

The same envelope `GET /api/v1/diy/pages/:id` answers — `id`, `name`, `kind`,
`title`, `content`, `schemaVersion`, `background`, `version` — so the renderer
needs nothing new. `kind` is always `user_center`. The newest **published**
page of that kind wins; a draft beside it is invisible.
`DIY_USER_CENTER_PAGE_MISSING` (404) when none has been published.

A fixed path rather than a slug on `:id`, which the CR offered as an
alternative: `id` is `^\d+$` across twenty-odd routes and widening it so one
caller may pass a word weakens it for all of them.

### `GET /api/v1/diy/navigation` — `auth: 'public'` (CR-3-h2 §2)

```
navigation  object | null   the saved `pageFoot` component, VERBATIM
version     string          the live home page's version; '0' when there is none
```

`navigation` is the component exactly as the operator saved it, after the
retired-component filter every storefront read applies. **Not** the CR's
`{ enabled, items, middle }`: `components/pageFooter/index.vue` reads
`effectConfig.tabVal`, `navConfig.tabVal`, `navStyleConfig.tabVal`,
`toneConfig.tabVal`, `menuList[].{name,link,imgList}`, `txtColor.color[0].item`,
`activeTxtColor`, `bgColor`, `bgColor2`, `fillet.{val,type,valList[0..3].val}`,
`topConfig.val`, `bottomConfig.val`, `prConfig.val`, `mbConfig.val` — a tidier
shape is a rewrite of that renderer, and the rule of this domain is that the
saved envelope crosses the wire untouched.

Taken off the **live home page**, matched case-insensitively on the component's
`name` (`pagefoot`), which is where and how the legacy `getNavigation` took it.
The fixtures store it under the literal key `"undefined"`, which is precisely
why the lookup is by `name` and not by key.

`{ navigation: null }` rather than a 404 when no home page is published: this
component is mounted on every tabbar page, and a shop mid-setup must not have
every screen erroring.

### `GET /api/v1/diy/layouts/:type` — `auth: 'public'` (CR-3-h2 §3)

`:type` is `category | user`. Response `{ status: 1 | 2 | 3 }`. Always answers;
an unconfigured shop gets `1`, which is what the legacy call's failure branch
fell back to.

## 2. Kit API added (CR-3-d2)

Exported from `@/admin/kit`:

| Name                             | What it is                                               |
| -------------------------------- | -------------------------------------------------------- |
| `EntityFormLoad<D>`              | `{ route, params?, select? }` — the record to load first |
| `FormModalDetail<T, D>`          | `{ route, params(record), select? }` for `useFormModal`  |
| `UseFormModalOptions<T, D>`      | `{ detail?: FormModalDetail<T, D> }`                     |
| `ModalForm` / `DrawerForm`       | both take `load?: EntityFormLoad`                        |
| `useFormModal<T, D>({ detail })` | builds the `load` from the clicked row                   |

Three states, and the middle one is the point: **in flight** renders a skeleton
and _no_ fields and _no_ 保存 button, **error** renders the message with a 重试
button and still no 保存, **loaded** renders the form seeded from the detail.
A half-populated form on screen is exactly the failure this exists to prevent.

`select` returns `Record<string, unknown>` rather than `Partial<z.input<S>>`:
the form schema and the detail route are independent type parameters and TS
cannot relate them at the call site without making every page annotate both.

> The brief says "`CrudTable` given a `detailRoute` alongside its update route
> wires it automatically". `CrudTable` has no update route of its own — the
> edit modal is a sibling component the page owns — so the automatic wiring is
> `useFormModal({ detail })`, which is one line on the page and needs no new
> prop on the table. Flagging it as a deviation from the brief's wording rather
> than its intent.

Documented in `apps/web/src/admin/kit/README.md` under
「编辑表单必须先把整条记录读回来（CR-3-d2）」.

## 4. The read-only config descriptor (N1's leftover)

`ConfigFieldUi` gains `readOnly?: boolean` and `source?: string`.
`site.publicOrigin` and `site.extraOrigins` are the first two users
(`env:PUBLIC_ORIGIN`, `env:EXTRA_ALLOWED_ORIGINS`).

Three independent pieces, on purpose:

1. `describeGroup` emits `readOnly: true` and folds `source` into `help`
   (`由部署环境决定：env:PUBLIC_ORIGIN`);
2. `<ConfigGroupForm>` renders such a field as plain text with **no control at
   all** — not a disabled `<Input>`, which reads as "not yet" and whose value
   antd would still carry into the payload — and `buildConfigPayload` drops the
   key;
3. `configSave` refuses the key with `CONFIG_FIELD_READ_ONLY` (422,
   `details: { keys }`), **on presence and not on difference**. "You may send
   it as long as it matches" would let a stale tab write the value the moment
   the environment changed underneath it.

Both fields used to be absent from the descriptor entirely. Showing them is the
deliberate half of the trade: an operator whose WeChat links point at
`http://localhost` has to see which host the shop thinks it is before they can
fix the variable that says so. `system.test.ts`'s
「is not an operator setting」 case was rewritten to state the new rule.

## Deviations, and why

1. **`logo` is an object of four slots**, not one string. The app renders four
   different logos (header, sign-in, share card, favicon) and the legacy config
   had four keys; one field would have meant the app picking a logo by guessing.
2. **A `filing` block was added** to `GET /api/v1/site/config`. The brief does
   not list it; the 工信部 footer is rendered on every H5 page and there is
   nowhere else for it to come from.
3. **`payments` carries `wechat` only.** WeChat Pay v3 is the only gateway in
   scope; Alipay and the rest are on the scope guard. The app's mapper should
   read every other legacy flag as `0`.
4. **Path `POST /api/v1/attachments/base64`**, as the brief says, not CR-7-h2's
   `/api/v1/site/image-data-urls`. The brief wins; both uni-app callers point at
   the CR's path today and are listed above.
5. **`mp.weixin.qq.com` is not on the allow-list**, although the legacy proxy
   accepted it. E2's `GET /api/v1/wechat/mini-qrcodes` already stores the QR as
   our own attachment, so the poster code fetches an URL this route trusts. The
   alternative was an allow-list entry for a host we do not control.
6. **One image per call.** The legacy endpoint took `{ image, code }` and
   returned two data URLs; two independent fetches behind one rate limit and one
   error code made the refusal unattributable.
7. **CR-3-d2's "`CrudTable` given a `detailRoute`"** is served by
   `useFormModal({ detail })` — see §2.
8. **`GET /api/v1/diy/layouts/:type` answers a number, not CR-3-h2 §3's
   boolean.** `pages/goods_cate/goods_cate.vue` tests
   `status == 2 || status == 3`, and the production fixtures carry
   `category: 1` and `member: 2`. A boolean would have collapsed two of the
   three values into one.
9. **`GET /api/v1/diy/navigation` returns the raw component**, not the CR's
   `{ enabled, items, middle }` — see §1.
10. **`DIY_USER_CENTER_PAGE_MISSING` is a new error code** rather than reusing
    `DIY_PAGE_NOT_FOUND` ("模板不存在"), which would send an operator hunting
    for a page they think they deleted.
