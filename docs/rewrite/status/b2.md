## Decisions other streams must know

1. **The fulfilment enum is `unfulfilled / partially_fulfilled / fulfilled`.**
   The brief's prose says `unshipped / partially_shipped / shipped`; the frozen
   `orders_fulfillment_status` PostgreSQL enum says the former, the schema is
   frozen, so the contracts spell it the way the database does. B1 already
   exports `orderFulfillmentStatus` with those three values and B2 reuses it.
2. **改价 takes a discount, never a total.** `orderPriceBody` is
   `{ operatorDiscount, freightAmount?, reason? }`. The server recomputes
   `payableAmount` with B1's own `payableOf` and re-splits the per-line shares
   with B1's `distribute`, so `sum(order_items.discount_amount) ===
   orders.coupon_discount` keeps holding to the fen and a later partial refund
   never has to re-prorate. Legacy wrote the operator's typed total straight
   onto `pay_price` and left the line shares stale; that is the defect being
   removed, which is why there is deliberately no "set the total" field.
   **Stream C:** a re-priced order's `couponDiscount` therefore includes the
   operator discount, exactly as CR-3-b1 already says for contributors.
3. **Virtual goods split three ways, and only one of them is shipped by hand.**
   `virtual_card` claims one `product_virtual_cards` row per order item and
   `virtual_coupon` grants the gift coupons, keyed on
   `product_virtual_cards_order_item_uq` and `user_coupons_order_gift_uq` so a
   replay cannot double-issue. Only `virtual_manual` reaches the 发货 form, and
   asking to ship a card or coupon line answers
   `ORDER_VIRTUAL_AUTO_DELIVERED`.

   **Corrected while implementing:** the contracts note above said the claim
   and the grant happen *in the paid hook*. They do not. `onOrderPaid` runs
   inside the paying transaction, so anything it does can roll a payment back —
   and running out of card keys is a legitimate, routine failure. The hook now
   records **one effect row and nothing else**
   (`order/<id>/order.auto-deliver`), and the ledger runs `autoDeliver` after
   the commit: it retries with backoff, parks the row for a human when the shop
   really is out of cards, and leaves the order sitting in 待发货 where an
   operator can see it. The idempotence gate is the order's own
   `virtual_delivered` timeline row, taken under the order lock.
4. **Export is CSV text inside a JSON envelope**, not a binary stream:
   `handle()` validates every response against its contract, so a route cannot
   answer with a file. The admin kit turns `content` into a download. Bounded by
   `order.exportMaxRows`. XLSX and a real streamed download need a kernel escape
   hatch — CR-2-b2.
5. **`/admin-api/express-companies` lives on B2's surface for now.** It is
   reference data (`express_companies`, seeded) that the 发货 form cannot do
   without, and stream F2's `shipping` domain does not exist yet. F2 should take
   the route over unchanged — CR-1-b2.
6. **Who is staff is a config list, not a role.** `order_notice_admin_uids`
   becomes the `orderStaff` typed config group; B2 registers a `StaffCheck`
   against it, which is what un-403s every `auth: 'staff'` route (p0a note 6).
   `GET /api/v1/staff/me` is `auth: 'user'` on purpose so the uni-app can ask
   "do I see the 商家管理 entry" without eating a 403.
7. **Three uni-app endpoints never existed and are not being created.**
   `admin/order/split_cart_info`, `admin/order/split_delivery` and
   `admin/order/offline` have no route in `crmeb/app/api/route/v1.php`. Stream H
   should delete `orderSplitInfo`, `orderSplitDelivery` and `setOfflinePay` from
   `template/uni-app/api/admin.js` rather than port them. Order splitting is
   gone shop-wide, so the admin-web split routes go too.
8. **The legacy parent/child completion cascade has no successor.** With no
   splitting there are no child orders, so `StoreOrderServices.php:1064-1076`
   is simply deleted.

## Decisions taken while implementing

9. **A dispatch cannot be walked backwards once the order is `shipped`.**
   `ORDER_TRANSITIONS` has no `shipped -> paid` edge and `transition` throws on
   an illegal one, so 撤销发货 is allowed only while the order is still `paid`
   — that is, while something on it is still outstanding. The correction for a
   fully shipped order is 修改发货信息 (`PATCH /admin-api/shipments/:id`), which
   is why that route exists. A buyer told 已发货 who then sees 待发货 opens a
   ticket faster than the operator can fix the waybill, so this is deliberate
   rather than a gap. `ORDER_SHIPMENT_NOT_EDITABLE` carries the reason.
10. **A card-key line is a one-card line.** `product_virtual_cards_order_item_uq`
    is UNIQUE on `order_item_id`, so one order item can hold exactly one card.
    `autoDeliver` claims one, logs a warning when `quantity > 1` and still marks
    the line delivered — the buyer gets their card and the operator sees the
    warning, rather than the order silently half-delivering. The real fix is at
    checkout: **CR-3-b2** asks A/B1 to cap a `virtual_card` line at quantity 1.
11. **One implementation, two surfaces.** 备注, 改价 and 修改地址 have a single
    service each; `operatorOf(ctx)` reads `ctx.actor` and records `admin` or
    `user` in `order_status_logs.operator_kind`. Legacy kept two copies
    (`AdminOrderController` and `admin/StoreOrderController`) and they drifted.
    The staff console reaches the same functions, and 改价 from the phone is
    additionally gated on `orderStaff.allowStaffRepricing` (off by default).
12. **`StaffRefundPort` is typed with stream C's own contract types**
    (`AdminRefundListQuery`, `PagedAdminRefunds`, `AdminRefundDetail`,
    `RefundApproveBody`, `RefundRejectBody`), not with `unknown`. The three
    `/api/v1/staff/refunds*` routes therefore validate against C's schemas
    today and start working the moment C calls `registerStaffRefundPort`.
    Until then they answer `INTERNAL` rather than a wrong shape.
13. **`refunded_quantity` is C's to write, under the mirror of B2's bound.**
    B2's dispatch uses `shipped + q <= quantity - refunded`; a refund approval
    must use `refunded + q <= quantity - shipped`. The race test writes that
    statement locally (`order.fulfil.concurrency.int.test.ts::approveRefund`)
    and proves B2's side holds against it either way round. **Stream C:** use
    that bound, and the CHECK `order_items_shipped_within_quantity` catches a
    mistake either way.
