## Panel API ready

**Stream G2 can start.** Everything below is frozen; changing any of it is a CR.

A config panel is a controlled component over **one node of the saved page**. It
receives the node, a setter and a context, and owns nothing else: it never
touches the editor store, never reads the rest of the page, and never calls a
route. Everything it needs arrives through `value` or `ctx`.

### `defineDiyPanel`

```ts
export interface DiyPanelDefinition<
  T extends DiyComponentValue = DiyComponentValue,
> {
  key: DiyComponentKey; // must be a key of diyComponentSchemas
  schema: z.ZodType<unknown>; // the component's schema from @shop/contracts
  createDefault: () => T; // fresh object each call; must satisfy schema
  Panel: DiyPanelComponent<T>; // ComponentType<DiyPanelProps<T>>
  label?: string; // palette label; defaults to the schema's cname
  description?: string; // one line under the palette entry
}

export function defineDiyPanel<T extends DiyComponentValue>(
  definition: DiyPanelDefinition<T>,
): AnyDiyPanelDefinition;
```

`DiyPanelDefinition<T>` is contravariant in `T` through `Panel`'s props, so a
heterogeneous array of panels has no useful common type. `defineDiyPanel` erases
`T` once, at the declaration site, and returns `AnyDiyPanelDefinition`. Panels
therefore stay fully typed inside their own file and are interchangeable outside
it. Do not re-annotate the export.

What a panel is handed:

```ts
export interface DiyPanelProps<
  T extends DiyComponentValue = DiyComponentValue,
> {
  value: T;
  onChange: (next: T) => void; // replaces the whole node; always a NEW object
  ctx: DiyPanelContext;
}

export interface DiyPanelContext {
  componentKey: DiyComponentKey; // always equals definition.key
  pageKind: DiyPageKind; // 'home' | 'user' | 'page' | ...
  theme: DiyTheme; // { theme, accent } — for "follow the theme" previews
  reset: () => void; // restore createDefault()
  remove?: (() => void) | undefined; // absent for the singletons (pageFoot, bottomMenu)
  disabled: boolean; // read-only page, or a publish in flight
}
```

`DiyComponentValue = Record<string, unknown> & { name?: string }` — deliberately
loose, because a saved node may carry keys this build has never seen and they
must survive the round trip. **A panel must never rebuild a node from scratch**:
spread the incoming value, change what it owns, and leave the rest alone.
`onChange` must be called with a new object; the store compares by reference.

### `bindDiyPanel`

```ts
const b = bindDiyPanel(value, onChange, ctx.disabled);

<DiySetUpTabs value={b.tab} onChange={b.setTab} />
<DiyColourField label="指示器颜色" {...b.bind('dotColor')} />
b.patch({ swiperConfig: next });
```

- `b.bind(key)` yields `{ value, onChange, disabled }` — exactly the
  `DiyFieldProps<V>` every field editor accepts.
- `b.patch(partial)` shallow-merges.
- `b.tab` / `b.setTab` read and write `setUp.tabVal`, which is how the legacy
  panels persist the 内容设置 / 样式设置 switch. It is saved state, not component
  state; the fixtures contain it.
- Not a hook. No state. Safe to call conditionally, cheap per render.

### Registering a panel

Two lines in `panels/index.ts`:

```ts
import myKeyPanel from './myKey.panel';
export const diyPanels: readonly AnyDiyPanelDefinition[] = [ …, myKeyPanel ];
```

Nothing else in the editor changes. Registration is an explicit array rather than
a `pnpm gen` glob: the shell has to boot with an incomplete set while G2 is still
writing panels, and a key with no panel must degrade rather than fail the build.
`panels/index.ts` and `panels/*.panel.tsx` are **G2-owned** from now on; G1 will
not touch them again except through a CR.

An unregistered key is not an error: `<DiyPanelHost>` falls back to `DiyRawPanel`,
a validating raw-JSON editor. That is also what the three render-only keys
(`newVip`, `presale`, `swipers`) get — they have no editor UI in the old admin
either — and what a page imported from a newer CRMEB build gets.

### Testing a panel

`panels/panels.test.tsx` runs a shared suite over `diyPanels`, so simply adding a
panel to the array gets it checked for:

- its `key` is a real component key;
- `createDefault()` satisfies the component's schema;
- `createDefault()` returns a fresh object each call;
- its default serialises byte-identically as a page node.

Add per-panel cases to the same file for anything conditional (a field that only
appears on one tab, a value that must stay an array, …). Use `renderAdmin` from
`@/test/render` and `<DiyPanelHost registry={diyPanelRegistry} … />` rather than
the panel component directly, so the test exercises what the editor does.

```
pnpm --filter @shop/web exec vitest run --project unit src/admin/diy
```

26 tests today, all passing.

### Hard rules for panels

1. **Never drop a key.** Spread, patch, return. The round-trip tests in
   `@shop/contracts` will catch it, but only if the node reaches them.
2. **Never coerce.** Production nodes store numbers as strings, `type` fields as
   arrays, and `info` as either a string or a row array. The schemas are
   deliberately permissive; a panel that normalises silently rewrites a
   customer's page.
3. **No defaults on read.** `value.foo ?? fallback` is fine for rendering; writing
   the fallback back into the node is not.
4. **All UI text in Simplified Chinese**, matching the legacy labels where one
   exists (`template/admin/src/components/mobileConfig/`).
5. **`timestamp`, `name`, `cname` belong to the store.** `createDefault()` returns
   the body only.

### Item 1 — schemas

`schema/primitives.ts` holds the legacy config vocabulary (`diyTabs`, `diyColour`,
`diySlider`, `diySelect`, `diyInput`, `diySpacing`, `diyFillet`, `diyUpload`,
`diyListBox`, `diyBorderConfig`, `diyShadowConfig`, `diyComponentBgConfig`, …) and
`defineDiyComponent(key, shape)`, which pins `name` to the key and merges the
shared base and style shapes.

Three rules govern every schema in this directory:

- **Everything is loose** (`z.looseObject`). Unknown keys are kept.
- **Nothing is defaulted, coerced or transformed.** Not one `.default()`,
  `.catch()`, `z.coerce` or `.transform()` in the tree.
- **Numbers may arrive as strings** and vice versa; selections may arrive as
  arrays. The schemas widen rather than normalise.

`schema/registry.ts` exports `diyComponentSchemas` (33 keys, admin palette order),
`DIY_COMPONENT_KEYS`, `RENDER_ONLY_COMPONENT_KEYS` (`newVip`, `presale`,
`swipers` — the uni renderer knows them, the admin has no palette entry),
`ADMIN_ONLY_COMPONENT_KEYS` (`bottomMenu`), `CREATABLE_COMPONENT_KEYS` (28,
i.e. 33 − 3 render-only − `pageFoot` − `bottomMenu`, both singletons),
`RENDERABLE_COMPONENT_KEYS` (32) and `isDiyComponentKey`.

A node is dispatched by `name` with a `.check()` on a loose object rather than a
`z.union`. A union's permissive last branch swallowed malformed known components
(`{name:'titles', isHide:'yes'}` passed); the dispatch re-raises the registered
schema's own issues at the right path, and a node whose `name` is unknown is
accepted verbatim.

`schema/page.ts` holds the envelope. Two functions carry the whole
byte-compatibility guarantee:

```ts
export function parseDiyPageValue(input: unknown): DiyPageValue {
  const result = diyPageValue.safeParse(input);
  if (!result.success) throw new DiyParseError(result.error.issues);
  return input as DiyPageValue; // zod reorders keys on a loose object; the bytes matter
}
```

**`parseDiyPageValue` returns the caller's own object**, never zod's output. zod
v4 rebuilds a loose object with known keys first, which silently reorders
`JSON.stringify` output. Validation must not be allowed to rewrite a page.

Also there: `safeParseDiyPageValue`, `serialiseDiyPageValue`,
`diyPageEntriesInOrder` (render order: numeric `timestamp` ascending, NaN last,
ties broken by key — not key order; `prod-7` proves the two differ) and
`reindexDiyPageValue`.

`schema/legacy.ts` describes the `eb_diy` row for the ETL.

**`cleanDiyData` is a port, not a rewrite.** The PHP walks the page, drops any
node whose `name` is in `core_store_removed_pages.json`, and rewrites the link
of anything pointing at a removed storefront route. Ported branch for branch,
with `packages/core/src/diy/__fixtures__/clean-parity.json` holding the input
and the expected output, so the parity test fails if either side drifts.

**Optimistic concurrency.** `savePageContent` takes the version the editor
loaded and updates conditionally on it; a loser gets `DIY_VERSION_CONFLICT`
rather than silently overwriting. One `runConcurrently` race proves exactly one
of several simultaneous saves wins (DIY-004). It is the only conditional state
change in the domain, which is why there is no separate
`diy.concurrency.int.test.ts`: publishing, set-home and the theme switch are
all single-row updates behind unique indexes that the database itself decides.

## Decisions

Recorded here rather than asked, per the brief.

1. **No zustand.** Adding it means editing `apps/web/package.json` and the
   lockfile, neither of which this stream owns or may commit. The editor store is
   `useReducer` + context, with undo/redo as past/present/future. **No new
   dependency anywhere in G1**; `@dnd-kit/*`, antd 6 and `@tanstack/react-query`
   are already installed.
2. **`parseDiyPageValue` returns its input.** See above. Any future helper that
   validates a page must do the same, and no DIY schema may ever gain a default,
   coercion or transform. This is the invariant the whole stream rests on.
3. **Panels are registered explicitly**, not globbed, and `panels/**` transfers to
   G2.
4. **Pickers go through a port** (`DiyDataSource`), not through routes, with a
   stub fallback, so G2 is not blocked on the product/coupon/article streams.
5. **`DiyLinkField` stores a bare path string**, e.g. `/pages/goods_details/index?id=1`,
   because that is what the legacy payloads and the uni renderer use. It is
   deliberately not the admin kit's structured `LinkValue`; the kit's `LinkPicker`
   is used underneath and the value is flattened on the way out.
6. **The raw JSON fallback is permanent**, not a placeholder. Losing an
   unrecognised node on save would be data loss.
7. **`diySelection = number | string | unknown[]`.** Production stores
   `checkboxInfo.type`, `goodsLabel.activeValue` and `couponTime.val` as arrays,
   and `imgConfig.info` and friends as bare strings, where the defaults are
   scalars. The schemas widened to match the data, not the defaults.
8. **Restore-default reads the theme, not the row.** Legacy kept a second copy of
   every page in `eb_diy.default_value`. Here 还原默认 takes
   `themes.default_data[<surface>]` of the active theme, and 设为默认数据 writes
   it back. One factory copy per surface per theme instead of one per page, which
   is what an operator means by "the default"; `DIY_NO_DEFAULT_CONTENT` says so
   when a theme has none. The ETL counts the `default_value` payloads it leaves
   behind.
9. **The version token is `<updated_at in ms>-<envelope version>`.** Two parts
   because the envelope carries its own `version` hash that the renderer already
   polls (legacy `get_diy_version`), while the row's `updated_at` is what makes a
   save detectable when the content did not change. Opaque to the client: compare
   it, never parse it. The same string is the weak ETag on the storefront read.
10. **`jsonb` reorders the keys inside a node** (CR-1-g1). Byte-exactness is a
    wire-layer guarantee: what goes in comes back with every key and value intact
    but possibly re-ordered, which the renderer does not care about because it
    sorts by `timestamp` itself. Tests at the HTTP and service layers assert deep
    equality; the byte comparison lives in `@shop/contracts`.
11. **Dehydrate on save, never hydrate on read.** The editor hydrates product and
    article lists to draw a preview; `dehydrateDiyContent` strips them back to
    ids before storing, so the saved page never carries a stale product title.
    The storefront read resolves nothing either — stream H's renderer fetches by
    id, exactly as the legacy app does.
12. **Adding a component is a click, not a drag.** The legacy palette dragged
    into the canvas; reordering inside the canvas is still a drag (dnd-kit), but
    a palette entry inserts after the selection. Dragging between two scroll
    containers was the part operators complained about, and it is the part that
    breaks on a trackpad.
13. **Timestamps are rewritten only when the order is no longer ascending.**
    Legacy `diyIndex.vue:739` restamps every node on every save, so an untouched
    page came back different. Here `stampNodes` restamps only when a move really
    happened, which is what makes an open-and-save round trip byte-identical
    (DIY-005). `id` follows `timestamp` as `'id' + timestamp`
    (`mobildConfig.js:445`).
14. **The footer is state, not a node in the list.** A home page always ends with
    `pageFoot` and a product-detail page with `bottomMenu`
    (`diyIndex.vue:1180`). Lifted out on load, re-appended last on save, and
    pushed past the body if a restamp would otherwise sort it to the top
    (DIY-007).
15. **Previews are schematic.** Reimplementing the uni-app renderer here would
    mean maintaining two renderers that must agree pixel for pixel, and the one
    that matters would still be the other one. The 预览 QR code opens the real
    page.
16. **`createDiyLinkSource` needs a `targets` callback.** The registry half
    (categories + links) is served by this stream. The dynamic half — pick a
    product, an article, a coupon — is a `listTargets` callback the owning stream
    injects; the legacy picker's dynamic groups (商品, 文章, DIY页面, 抽奖) are
    therefore **not** migrated as registry rows, and the ETL reports them.
17. **The admin components live in `src/admin/diy/**`,** not beside the page
    files as the golden slice's coupon pages do. The brief names that directory
    as this stream's, and the editor is a module of 25 files with a frozen public
    API for G2 rather than one screen. The three files under
    `app/admin/(shell)/diy/` are thin server components.
