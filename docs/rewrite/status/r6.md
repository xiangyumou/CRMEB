## §1 — CR-1-h4 (category-scoped coupons on 确认订单)

- `core/src/coupon/coupon.service.ts` `listApplicable`: each line's categories come from
  `coupon.repo.ts` `productCategoryIds` (a batched read of `product_categories_map`, the same rows
  the catalog's `CatalogPort` hands checkout, so the picker and the order agree). The body's
  `categoryIds` is never read.
- Why a repo read rather than `@shop/core/catalog`: catalog → order → coupon already import each
  other in that direction; coupon → catalog would close the cycle. `groupbuy.repo.ts`,
  `presale.repo.ts` and `stats.repo.ts` read catalog tables the same way.
- `contracts/src/coupon/schemas.ts` `couponCartLine.categoryIds` is `.optional()` and documented as
  ignored; the route example no longer sends it.
- Tests: `coupon.int.test.ts` › `listApplicable › CR-1-h4 — …` (usable with `categoryIds` omitted;
  not usable when the client claims a category the product is not in);
  `apps/web/app/api/v1/user-coupons/applicable/applicable.int.test.ts` (new, the same two over HTTP
  plus a 401).
- uni-app: `api/mappers/coupon.js` `fromLegacyApplicableInput` stops sending `categoryIds`; the
  `it.fails` in `tests/mappers.misc.test.mjs` is deleted and replaced by an `it` that asserts no
  line carries it. `tests/fixtures/contract-examples.json` regenerated (`npm run fixtures`; it also
  picks up R1's `readyz` backlog example).
- Storefront: `cart-checkout-pay.spec.ts` › `a shopper applies a category-scoped coupon on the
confirm page` — a ¥7 品类券 on the seeded category is auto-applied over the ¥5 store-wide one
  (¥38.00), and the picker lists both. Arranged through the coupon service and removed in
  `finally`, because every seeded product sits in that category.

## §2 — CR-2-h4 (what the shopper paid per unit)

- Fix (1) of the CR, without a migration: the create path keeps each checkout rule's share of each
  line in `order_items.snapshot.adjustments` (jsonb; `OrderItemSnapshot` in
  `db/src/schema/order.ts` gains an optional field — a type-only change, no SQL).
  - `order.pricing.ts`: `AppliedAdjustment` gains `perLine` (negative, aligned with the lines,
    summing to `amount`) — the split `splitAdjustments` already computed and threw away.
  - `order.checkout.service.ts` `create` (the `insertOrderItems` mapping only — not `buildDraft`):
    `snapshot: { ...snapshotOf(sku), adjustments: lineAdjustmentsOf(draft.discount, index) }`.
  - `contracts/src/order/schemas.ts` `orderItem.adjustments: priceAdjustment[]` — per line, in the
    order applied; they sum to `-discountAmount` (except after 改价, which redistributes
    `discountAmount` and leaves the record of what checkout applied); `[]` for a line written
    before this change. `order.query.service.ts` and `order.console.service.ts` `toOrderItem` read it
    from the snapshot, so the create answer, `order.list`, `order.detail` and the console reads
    carry the same items.
- Why not fix (2) (store the activity unit price): it breaks either `coupon_discount =
sum(discount_amount)` or the meaning of `originalUnitPrice` (划线价) that refunds and invoices
  read. Why not an order-level `adjustments`: the client folds the per-line entries itself, and a
  per-line record is what a multi-line order needs.
- uni-app `api/mappers/order.js`: `orderActivityDiscountCents` sums the `*:activity-price`
  entries over the lines when any line carries adjustments; otherwise the old single-line
  fallback (non-normal kind, no coupon) still applies. `toLegacyOrderItem` uses the line's own
  entries; `toLegacyOrderListItem` computes the order's activity discount itself, so the 订单列表
  and 订单详情 print the same ¥78 (and the staff mapper, which calls both, follows).
- Tests:
  - `core/src/order/order.pricing.test.ts` › `keeps each adjustment's own per-line share…`.
  - `core/src/order/order.adjustments.int.test.ts` (new, 3): a presale ¥88→¥78 with a ¥5 coupon
    reads `[presale:activity-price −10.00, coupon:discount −5.00]` on create, detail and list, and
    list items equal detail items; an ordinary two-line order's coupon split sums per line to
    `discountAmount`; no discount → `[]`, and a snapshot without the field reads `[]`.
  - uni-app `tests/mappers.order.test.mjs`: `CR-2-h4: a 预售 order with a stacked coupon still
prints ¥78` flipped from `it.fails` to `it` (also pins `total_price 78.00`, `coupon_price
5.00`, `pay_price 73.00`); new `CR-2-h4: the 订单列表 prints the activity price too`; the
    pre-CR-2-h4 fallback is pinned.
  - Storefront `presale.spec.ts` › `a presale with a stacked coupon still shows the presale price
on the order pages`: a ¥5 coupon scoped to the activity product is granted, the presale order
    is created through the checkout API with it (the confirm page never picks a coupon for an
    activity), the create answer separates the two entries, 订单详情 prints ¥78.00 with a
    优惠券抵扣 row and ¥73.00, and the 待付款 list card prints ¥78.00 and no ¥88.00. The order is
    cancelled and the coupon revoked in `finally`.
- E2E fixture fix found while landing the journey: `src/fixtures.ts` `seedToken` seeded only the
  token. A real login also commits `SETUID`, and `pages/goods/order_list` hides a card's line prices
  and total when `gift_uid (0) === $store.uid (0)`, so every order looked like a gift the shopper had
  received. `seedToken(page, token, userId)` now seeds `UID` as well, for both shoppers. The app
  was fine; only the harness login was incomplete.
- Not added: a 拼团 + coupon case — it takes the same contributor → `splitAdjustments` →
  snapshot path as the presale one.

## §4 — the staff 售后 screens follow `allowStaffRefundReview`

- Nothing carries a staff switch to the app. `allowStaffRepricing` never reached it either: both
  switches are read only where the staff service refuses. `GET /api/v1/staff/me` answers
  `{ isStaff, userId, nickname }`, the refund reads are C's console shapes, and
  `/api/v1/site/config` is public. As the brief says, this is CR'd rather than invented:
  **`docs/rewrite/cr/CR-1-r6.md`** proposes `staffIdentity.abilities: { refundReview, adjustPrice }`,
  filled by `order.staff.service.ts` `me` from `orderStaffConfig`.
- The app side is done against that proposal, so resolving the CR is server-only:
  - `api/mappers/staff.js` `toLegacyStaffIdentity` → `refund_review` is 1 only when `isStaff` and
    `abilities.refundReview === true`. It is 0 when the field is absent, which is the switch's
    default.
  - `pages/admin/refund_order_list` and `pages/admin/refund_order_detail` call `getStaffIdentity()`
    on load (`canReview`, false until it answers) and show 退款审核 / 确认收货 only when it is on.
    查看物流 and 订单备注 stay.
- Test: `tests/mappers.staff.test.mjs` › `refund_review — the 售后 screens follow
allowStaffRefundReview` (on / off / absent / not staff).
- Until CR-1-r6 lands, a shop that turned the switch on also sees no review buttons on the phone.
  Before R2 no shop had phone review, so nothing that worked before is lost. 改价 gating on

## Ledger text (for the orchestrator's `invariants.md`)

- **ORDER (CR-2-h4):** for a line written at checkout, the entries in
  `order_items.snapshot.adjustments` sum to `-discount_amount`. There is one entry per applied rule,
  in application order, and an entry whose share is zero is omitted. 改价 redistributes
  `discount_amount` and leaves the entries as a record of what checkout applied. A line written
  before CR-2-h4 reads `adjustments: []`.
  Pinned by `order.adjustments.int.test.ts` and `order.pricing.test.ts`.

  (`outcome: 'succeeded'`), whichever way it succeeds: filled, expired with virtual fill, or 立即成团.
  Pinned by `groupbuy.smoke.int.test.ts` › `CR-3-h4`.
