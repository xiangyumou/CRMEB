## Decisions taken

The contracts in `contracts/src/stats/` were frozen before this stream started;
everything below is about how they are computed, not about their shape.

### 1. 营业额 is bucketed where the money moved, not where the order was paid

F2's status file held two decisions that cannot both be true:

- **16.** `revenue = Σ(orders.paid_amount − orders.refunded_amount)` bucketed by
  `orders.paid_at`;
- **17.** refund figures read `refunds.status = 'succeeded'` / `succeeded_at`.

Under 16 a refund lands on the day the *order* was paid, under 17 on the day
the *money* went back, and one page cannot show 营业额 = 商品支付金额 −
商品退款金额 under both. F3 keeps 17 and computes

```
营业额 = Σ paid_amount (orders paid in the bucket)
       − Σ refunds.refunded_amount (refunds succeeded in the bucket)
```

so **a day's figure never changes retroactively**: an operator reading last
month's chart sees the same numbers next month. Under 16, refunding a
January order in March rewrites January. Written up in
`core/src/stats/DEFINITIONS.md` §2; if the orchestrator prefers 16, the change
is one predicate in `stats.repo.refundAggregate` and one line in the service.

### 2. Money in a statistics response is a rounded `number`

Already settled by the frozen contract (F2's decision 19, and the long comment
in `contracts/src/stats/schemas.ts`). The repo casts every sum to `float8` and
the service rounds to two decimals once, at the edge.

### 3. Two figures are defined but have no writer yet — CR-1-f3

Nothing in the system writes `user_visits` (page views, geo, dwell time) or
`product_events` rows of `kind = 'cart'`. They are **kept and defined** rather
than dropped, because the tables exist, the SQL is written and tested, and the
gap is one insert in somebody else's domain:

| Figure                   | Needs                                  | Owner          |
| ------------------------ | -------------------------------------- | -------------- |
| 访客数 / 浏览量 / 地域访客 | a storefront page-view recorder        | orchestrator   |
| 加购件数                  | a `cart` product event on add-to-cart  | B1 (`cart`)    |

`cart_items` is **not** a substitute for the second one: the row is deleted
when the order is placed, so yesterday's additions vanish from history exactly
when they start to matter. Retired figures are a different thing and are
dropped, not zero-filled — see DEFINITIONS §5.

### 4. Exports: a ranking truncates, a time series refuses

CR-2-b2's envelope, and `stats.exportMaxRows` (2000) caps both. The two behave
differently on purpose:

- **商品统计导出** is a ranking, so the first `n` rows are a truthful answer to
  "the top sellers": it caps and sets `truncated: true`. It also ignores the
  query's `limit`, which sizes the table on screen — an operator exporting a
  file wants the window's products, not the twenty rows already in front of
  them.
- **交易统计导出** is a time series, and the tail of a series is not optional:
  over the cap it refuses with `STATS_EXPORT_TOO_LARGE` and asks for a
  narrower window.

CSV cells starting `=`, `+`, `-` or `@` are prefixed with `'`: a product named
`=1+1` is a formula injection in every spreadsheet that follows Excel.

### 5. Region rows carry three different notions of "province"

`totalUsers` / `newUsers` from the user's default address, `visitors` from
`user_visits.province`, `paidAmount` from `orders.receiver_province`. Each
column uses the province that column actually knows; pretending one join could
serve all three would silently drop every buyer without a saved address.
Unknowns are grouped as **未知** and sorted last whatever the sort key.

### 6. No worker job

This domain writes nothing, so it has nothing to sweep: `product_events`
retention is the catalog domain's `catalog.pruneHistory`, and `user_visits` has
no writer at all yet. When a visit recorder lands, `stats.pruneVisits` lands
with it and its `delete` goes in a separate `stats.retention.repo.ts` so
`stats.repo.ts` stays `select`-only — a claim worth being able to check by
reading one file.

### 7. Permissions

`stats:{user,product,trade,order}:read` and `stats:{product,trade}:export`,
exactly the atoms F2 declared in its status file (decision 20). Export is its
own atom because reading a page and walking out with the window as a file are
different acts. The dashboard tiles ride on `stats:trade:read`, so whoever may
not open 交易统计 does not learn today's revenue from the home page instead.

### 8. A fixed +08:00 in TypeScript, `at time zone 'Asia/Shanghai'` in SQL

Mainland China has observed no daylight saving since 1991, so the two agree on
every boundary this database can contain. `stats.int.test.ts` pins the
agreement with orders paid at 23:30 and 00:30 Shanghai — one UTC day, two
Shanghai days.
