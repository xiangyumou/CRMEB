### Things other streams must read

1. **The two OA webhook routes do not go through `handle()`.** WeChat wants the
   bare `echostr` as `text/plain` for the handshake, and either the five ASCII
   letters `success` or an XML document for an event. `handle()` always
   serialises JSON, so those two route files build their `Response` themselves
   and keep one line of logic. They are declared in contracts anyway, because
   the OpenAPI document is what tells an operator which URL to paste into
   公众平台 → 服务器配置. `response` is `z.string()`: the literal body bytes.
2. **`POST` takes no `body` schema**, for the same reason C's pay webhooks take
   none: in 安全模式 the signature covers the exact bytes and `handle()` would
   consume the stream.
3. **Menu save and menu publish are two routes.** The legacy screen did both in
   one button, so a WeChat outage lost the operator's edits.
4. **`wechat_media` is a mapping, not a second media library.** The upload route
   takes an **attachment id** (F1's `attachments`), not a file: the bytes are
   already ours, and a second multipart endpoint would be a second place to get
   the MIME check wrong.
5. **Reading never mutates, on either inbox.** The legacy `jnotice` marked new
   orders seen the instant the badge polled (`Common.php:213-214`), so polling
   twice lost the badge, and `getMsgDetails` flipped the read flag on fetch.
   Here only `POST …/read` and `POST …/read-all` change read state, and both
   answer `{ marked: n }` so a double tap reads `0`.
6. **The storefront resource is `my-messages`, not `messages`.** The id space is
   global and the rows are per-person; `GET /api/v1/messages/5001` invites
   exactly the bug where somebody else's id returns somebody else's message. A
   row belonging to another user answers 404, never 403.
7. **The send log is the effects ledger**, filtered to `scope = 'notification'`
   — see the decisions below.

## Decisions (binding for this stream)

1. **The OA management code lives at `core/src/wechat-oa/`, contracts at
   `contracts/src/wechat-oa/`** — not at `wechat/oa` as the brief spells it.
   The `boundaries/core-cross-domain` ESLint rule resolves a cross-domain
   import against `<domain>/index.ts`, so a directory nested inside stream C's
   `wechat` domain is not reachable under that rule (C hit the same thing and
   recorded it as its decision 3). C's client is imported through
   `@shop/core/wechat`'s index — relative `../wechat` from inside `core`.
2. **Permission atoms are `wechat-oa:*`.** `definePermissions` accepts a
   hyphenated domain, and matching the directory name keeps the atom
   greppable from the route.
3. **The send log is read from the effects ledger, not from a new table.** A
   notification is one ledger row per `(event, aggregate)`, and the ledger
   already carries the attempt count, the last error and the parked state. A
   parallel `notification_logs` table would be a second copy of that truth that
   could disagree with it, and it would need a schema change this stream is not
   allowed to make. `/admin-api/notification-logs` is therefore
   `scope = 'notification'` over `effects`, with the same
   list/retry shape C built for `/admin-api/payment-effects` — one domain
   should not claim the whole `effects` resource.
4. **The admin inbox routes declare `auth:profile:read`**, which every
   authenticated admin holds implicitly, because the bell must work for an
   account with no grants at all. The service scopes every query to
   `ctx.actor.id`. *Which* events reach an admin inbox is a permission
   decision, and it is made at fan-out time against the event's own atom.
