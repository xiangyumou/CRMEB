## Decisions other streams must know

- **`preview` and `create` take the same body.** There is no preview token and
  no server-side draft. `create` recomputes everything and, when the client
  sends `expectedPayableAmount`, refuses with `ORDER_PRICE_CHANGED` if the
  recomputation disagrees (risk matrix §1, "SKU swap between confirm and
  create").
- **`idempotencyKey` is required on `order.create`.** 8–64 chars of
  `[A-Za-z0-9_-]`. A replay returns the first order, 201, unchanged. It is
  stored on `orders.idempotency_key` and enforced by
  `orders_idempotency_uq (user_id, idempotency_key) WHERE idempotency_key IS NOT NULL`:
  the insert carries the key, a simultaneous twin blocks on the index entry and
  is answered with the winner's order, and a submit that rolled back leaves the
  key free to try again. A sequential replay is answered by a read before the
  draft is built, because by then the cart it would have priced is empty.
- **`orders.coupon_discount` holds every goods-level discount**, not only the
  coupon: coupon + each `PricingContributor`. The per-line
  `order_items.discount_amount` shares sum back to it exactly
  (`Money.allocate`). `payable = items + freight - couponDiscount`.
  C and B2 read it that way; the `adjustments[]` array on the preview is the
  itemised breakdown for the UI. See CR-3.
- **Cancelling is a two-call protocol** (CR-7-c). First, *outside* any
  transaction, `PaymentPort.closeOrderPayments(ctx, orderId)` asks the gateway
  to close every open attempt — it talks to WeChat, and a row lock held for a
  gateway round trip is how a checkout table seizes up. Then, under the order's
  row lock, `PaymentPort.ensureNoOpenAttempts(tx, orderId)` re-asks; it is
  database-only by contract and it is what catches an attempt that opened in
  between. **Both calls read the same decision table**: `closed` → transition,
  then release the stock and then the coupon, all in the same transaction;
  `paid` → throw `ORDER_ALREADY_PAID` and release nothing; `unknown` → throw
  `ORDER_PAYMENT_STATE_UNKNOWN` and release nothing. A paid order is never
  cancelled at all — `ORDER_TRANSITIONS` has no such edge, and it leaves
  through C's full refund.
- **`sweepExpiredOrders` closes five gateways at a time and then cancels one at
  a time.** The closes are the only part that leaves the database, so they are
  the only part that is parallel; the cancels are row-locked work and stay
  sequential. An order whose close did not answer `closed` is counted in
  `skipped`, releases nothing and is retried next pass. The report is
  `{ scanned, cancelled, skipped }`.

## More decisions other streams must know

- **The cart depends on the order domain, never the reverse.** The cart needs
  live catalogue data and the order needs cart rows; pointing both arrows makes
  the module graph circular. So: the catalogue seam is re-exported from
  `order/index.ts` and the cart imports it from there; the two `cart_items`
  statements checkout needs (`selectCartLines`, `deleteCartLines`) live in
  `order.repo.ts`; `cart.rebuy` calls `order.rebuyLines`. When stream A lands a
  real `catalog` domain, both import that instead and the coupling disappears.
- **`ctx.platform` is translated at the boundary.** The contracts speak
  `'wechat-mini' | 'wechat-oa' | 'h5'`; the `orders_platform` enum spells the
  first two with underscores. `order.checkout.service.ts` holds the one
  translation map. **B2 and C store the same column** — use the same map rather
  than writing a second one.
- **An unsellable cart row is shown, never silently dropped**, with a `state`
  (`ok` / `off_shelf` / `deleted` / `out_of_stock` / `limit`) the storefront
  greys out. 全选 ticks only sellable rows; 全不选 clears everything, dead rows
  included.
- **Cart prices are read live through the catalogue port**, never stored on the
  row. Legacy's `cart_info` JSON blob is not reproduced.
- **`preview` writes nothing.** It takes no lock and reserves no stock, so two
  shoppers can both be shown the last unit; `create` is where the loser finds
  out (`ORDER_OUT_OF_STOCK`). That is deliberate — reserving at preview lets
  anyone freeze a catalogue by opening confirm pages.
- **The purchase-limit check is advisory.** `per_order` and `lifetime` limits
  are read-then-write, so a determined buyer submitting twice at once can beat
  them by one order. The limits are a merchandising rule, not an invariant;
  stock is the invariant and stock is conditional. If a limit ever has to be
  hard, it needs its own counter row and a conditional update.
- **Auto-cancel is enqueued after the creating transaction commits**, so a
  rolled-back order never leaves a job behind.

## CR-7-c — cancelling an order that has a live WeChat payment

Stream C filed it and the orchestrator accepted it; it is applied here and
`docs/rewrite/cr/CR-7-c.md` records the detail.

The defect was not in a branch, it was a missing call. `ensureNoOpenAttempts`
is database-only on purpose — it runs under the order's row lock — so it
answers `unknown` for any order with an open attempt rather than going to find
out, and the caller is meant to have run `closeOrderPayments` first. B1 never
did. The order that never reached WeChat cancelled fine; **the buyer who tapped
立即支付, saw the sheet and closed it could not cancel at all**, and neither
could `autoCancel` or the sweep, so those orders sat on real stock until a human
noticed. That is the common case, not an edge.

What changed:

- `PaymentPort` gained `closeOrderPayments(ctx, orderId)`, registered by C's
  `registerPaymentDomain()`. `fakePaymentPort` answers both halves and records
  them separately (`calls` / `closes`), with a `closeResult` option for a test
  that wants the close to succeed and the re-check under the lock to differ.
- `cancelOrder` closes before it opens the transaction; `autoCancel` inherits
  it; `sweepExpiredOrders` closes five at a time and skips what it cannot
  close.
- `order.cancel.payment.int.test.ts` runs all of it against C's real payment
  domain and the fake WeChat gateway, on real orders from this stream's
  checkout — so the stock and the coupon it asserts on are ones that were
  genuinely taken. It also asserts the gateway is called exactly once per
  cancel, which is what keeps the re-check honest about being database-only.
- `payment.concurrency.int.test.ts` no longer keeps a local copy of the
  protocol; `QUEUE-003` and `TLS-006` race the real `cancelOrder`.

One decision worth recording: the sweep pre-closes, then calls `cancelOrder`,
which closes again. The second close is a database read that finds nothing open
— and the honest gateway call if an attempt opened in between. Passing the
first answer through would have saved that read at the cost of a parameter that
lets a caller assert `closed` without having earned it.

## CR-3-b2 — one card key per order line

B2 filed it; `docs/rewrite/cr/CR-3-b2.md` has the detail. Most of B1's half was
already in place — `cart.rules.ts` and `assertSellable` have refused a
`virtual_card` above quantity 1 since the domain landed — so this was about the
gaps rather than the rule.

- `capFor` returns 1 for a card product. It is the clamp `addUnits` applies and
  the cap 再次购买 rebuys against, and it was the one place the kind was not
  consulted.
- 立即购买 gets its own test. Buy-now never touches the cart, so the cart's
  refusal does not cover it; the cap is in `assertSellable`, where both sources
  meet.
- The cart's **edit** path gets one too: `updateItem` sets an absolute
  quantity, which is how you would walk round an add-time refusal.
- And one end-to-end: a single card through B1's checkout, paid, then B2's
  `autoDeliver` claims exactly one key and leaves the second on the shelf.

Two decisions recorded against the CR's suggestions. The error stays
`CART_VIRTUAL_CARD_QUANTITY` / `ORDER_VIRTUAL_CARD_QUANTITY` rather than
`ORDER_PURCHASE_LIMIT_REACHED`: a 卡密 cap is a schema fact, not a limit an
operator set, and `details: { limit }` would be a lie. And the cap is **not**
spelled as a forced `purchaseLimitMode: 'per_order'` / `purchaseLimitQuantity: 1`
on the product row, because that puts a schema invariant into operator-editable
data where the next edit can switch it off.
