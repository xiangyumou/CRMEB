### CR-3-k2, CR-4-k2, CR-5-k2 — the two webhooks

- **CR-3-k2.** Event type checked before the callback row: payment takes
  `TRANSACTION.*`, refund `REFUND.*`; anything else → 200, no row.
- **CR-4-k2.** `mchid` present and equal to the attempt's / refund's frozen
  merchant (configured one otherwise). Mismatch → callback row under the named
  merchant with `result: exception: merchant_mismatch …`, no settlement, no
  automatic refund, an operator notification, 200. New admin notification
  events, registered by the owning domains through
  `registerNotificationEvents` (the extension point the notification registry
  documents): `admin_payment_notify_mismatch` (`payment:exception:read`) and
  `admin_refund_exception` (`refund:request:read`, link `/admin/refunds/{{refundId}}`).
  No `payment_exceptions` row for a foreign merchant: that row carries an
  automatic refund, and a new enum reason would need a migration.
- **CR-5-k2.** `amount.refund` (webhook) and `refundFen` (query) compared with
  the frozen amount. Mismatch/absent → status unchanged, `last_error`, one log
  entry, one notification (idempotent on the message across sweeps), 200 /
  `unknown`.
- **Tests.** Flipped the four `it.fails` in `refund.webhook.int.test.ts`
  (K-SEC-P6 ×1, K-SEC-P7 ×2, K-SEC-R6 ×1). Changed the body (not the title) of
  `K-SEC-R6 … > can never change the amount booked: settlement uses the frozen amount`.
  Added six cases (see the CR files).
- **Left.** Exception refunds' notified amount (payment domain) not compared;
  no admin action closes a refund held by a mismatch (product question). Both
  in CR-5-k2.
